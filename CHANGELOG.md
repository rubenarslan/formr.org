# Formr.org Change Log (check previous change logs in CHANGELOG-v1.md)

The format is based on [Keep a Changelog](http://keepachangelog.com/) and this project adheres to [Semantic Versioning](http://semver.org/).

## [v1.10.2] - 06.09.2026

Cross-tenant IDOR sweep over the admin run/survey/API paths, plus the review
of that sweep. The OSF integration is removed.

### Security
- **Run-unit identity is established only by a run-scoped lookup.** `RunUnit`'s constructor forgets a caller-supplied `id` / `unit_id` / `run_unit_id` that `find()` cannot place in the run, `create()` cannot re-introduce one, `modify()` / `removeFromRun()` / `delete()` carry a `run_id` predicate, `findByRunUnitId()` takes the authorised run, and the admin AJAX handlers 404 on a unit that is not in the run. Two ways around that gate found in review are closed too: a request-supplied `special` (the special-unit branch of `find()` tagged a *missing* row, which PHP turned into a found one) and a request-supplied `importing` flag (skips `find()` entirely; the admin entry points now strip it).
- **Reminders, participant deletion and reminder counts are scoped.** `Run::getReminderSession` accepts only the run's own ReminderEmail units and a session of the run; the monkey bar may only remind / delete the session whose code passed its gate; `RunSession::load` scopes an `id` lookup to its run; `getSentRemindersBySessionId` joins the run.
- **Email accounts stay with their owner.** An Email unit's `account_id` must belong to the run owner (one gate in `create()`, and `sendMail()` loads the account scoped to the owner, so rows written before the gate cannot send through another user's SMTP credentials); `EmailAccount` loads by `(id, user_id)` when a user is given.
- **OAuth: an empty client scope no longer means "everything".** Patch 078 clears `oauth_scopes.is_default`; `createClient()` refuses an empty scope list; and a legacy non-internal client stored with scope `''` is handed a scope no row can satisfy, so an explicit `scope=` request is refused too. The superadmin "issue credential" action grants every known scope explicitly. `ApiV0` checks `data:read` / `session:write`.
- **Smaller closures.** Run import `basename()`s `run_file_name`; `Run::deleteFile` is run-scoped; `SurveyStudy::loadByName` (by name only) is gone; the survey rename check is anchored and the survey-test token refuses a name that is not a bare identifier and requires exactly three fields on the way back; `google_file_id` is validated and escaped; `User::login` verifies the password before revealing the unverified state (and verifies it once); password-reset links honour their 2-day expiry; 2FA backup codes and referral codes compare strictly.

### Fixes
- A live unit session whose unit is no longer placed in the run (study swapped behind the placement, or a pre-F22 orphan) ends as `unit_removed_from_run` and the run moves on, instead of executing an identity-less unit (a 500 for a Survey).
- Every scalar item (`text`, `email`, `url`, `color`, `date`/`datetime`, `check`, `number`, …) rejects an array reply with an error instead of a TypeError 500; `number` keeps its own message for a required item.
- Testing a survey whose stored name is not a bare identifier explains itself instead of landing on a bare 403.
- The survey settings range checks no longer read undefined keys on a partial POST; an unknown `special` no longer `die()`s mid-response.

### Changes
- **The OSF integration is removed** (`Services/OSF.php`, `admin/osf`, `api/osf`, the run-settings OSF tab, `$settings['osf']`, the CSP allowlist entries). The `osf` table and `survey_runs.osf_project_id` column are left in place.

### Schema
- 078: `oauth_scopes.is_default = 0` for every scope.
- 079: `UNIQUE KEY name` on `survey_runs` (also in `schema.sql`, so fresh installs baselined past 079 carry it).

## [v1.10.1] - 04.09.2026

Seven fixes found while reviewing an unreleased feature branch against this
release line. All of them are bugs in v1.10.0 itself, so they ship on their own.

### Security
- **Run export shipped items of studies the exporter doesn't own.** `Run::export` attached `survey_data` for whatever `unit_id` it was handed, and the ids come from the browser (`AdminRunController::exportAction` decodes `$_POST['units']`), so any admin able to export one of their own runs could read another user's full item table — labels, choices, showifs, values — by editing the posted unit list. Items are attached only when `survey_studies.user_id` matches the run's owner.

### Fixes
- **A key that cannot be loaded no longer fatals the request.** `Crypto::getKey()` returns null when Halite can't load the key, and `encrypt`/`decrypt` passed that null into Halite's typed `EncryptionKey` parameter: the resulting TypeError is an `Error`, not an `Exception`, so `catch (Exception)` let it escape as a 500 on any encryption call (saving a mail account was the canary). Both short-circuit with a logged error now, and every catch around Halite is `\Throwable`.
- **The encryption key is found when it lives in a mounted directory.** `setup()` and `getKeyFile()` used `file_exists`, which is true for a *directory* at the key path — deployments that mount a volume at `formr-crypto.key/` and keep the key inside therefore skipped generation, failed to load the "key", and silently encrypted nothing. `getKeyFile()` resolves a directory to the file inside it; `setup()` generates on `is_file`. `Config::initialize()` also drops its memoized lookups so a re-initialize can't answer from stale settings.
- **A blank `choice_list` cell no longer fails the upload.** The reader stored `''` and `Item::validate()` (`choice_list !== null`) then rejected every non-choice item in a sheet that merely *has* the column: "You defined choices for this item, even though this type doesn't have choices." Blank cells store NULL, and the `Item` constructor normalises `''` to NULL so JSON imports and rows written by the old reader read the same way.
- **A survey upload reports *every* invalid item, not just the first.** `SurveyStudy::addItems` folded each item's validation result in with the array-union operator, which keeps only the first value at each numeric index — so a sheet with ten invalid items showed one error, and the author fixed them one re-upload at a time. Same for warnings.
- **The PWA prompt items no longer demand choices.** `add_to_home_screen`, `push_notification` and `request_cookie` declare `hasChoices` (they use a choice only as a button-label override), so validation refused them when written without choices, while `request_phone` refused them when written *with* one — a sheet using them imported as an item-less husk study. New `Item::$choicesOptional` exempts an item from both directions.
- **A non-scalar answer is rejected instead of fataling.** `Number_Item::validateInput` went straight into `trim(str_replace(…))`, which TypeErrors on PHP 8 when the reply is an array — a participant posting `age[]=1` turned the page into a 500. `Mc_Item`'s unknown-choice check also only ran for `is_string`, so a non-string scalar bypassed it entirely (not reachable from a browser form post, but from any JSON payload).
- **A survey JSON upload keeps file order.** Items without an explicit `order` / `item_order` stored NULL for both, and rendering is `ORDER BY item_order` — so a hand-written survey JSON or an older run bundle came out with its pages scrambled and `submit` items ahead of the items they close. Items now default to their position in the file, the rule the spreadsheet reader already applies per row.

## [v1.10.0] - 02.09.2026

### Added
- **Superadmin "Personal Data" overview** (`admin/advanced/personal_data`, Advanced → Personal Data): which admins collect what is likely personal data, in which runs and surveys, and from how many participants. An item is flagged when its *type* collects personal data by construction (`email`, `tel`, `request_phone`, `geopoint`, `file`, `ip`, `browser`, `server`, `referrer`, `push_notification`) or when a free-response item's name or label mentions a keyword — phone, e-mail, name, date of birth, postal address, IBAN, student/Prolific/MTurk/SONA IDs, in English and German (`PersonalDataAudit::KEYWORDS`; extend for your instance's vocabulary). Choice items are never flagged. The page opens with a per-admin summary (runs, participants, surveys, flagged items, categories), then lists each run's surveys with the flagged items and the reason each was flagged, so a "do you own a phone?" false positive is visible as such. Technical items (IP/browser/referrer/push) are collapsed to one muted line per survey. Participant counts are non-tester sessions per run and non-tester results per survey (`?` for surveys with no metrics row yet). It is a heuristic over item definitions, not a PII detector: a text item labelled "Tell us about yourself" is invisible to it.
- Only the logged-in superadmin's own runs and surveys are linked from the page; the admin run/survey pages resolve names against the current user, so links to other admins' objects would 401/404. Other admins' objects show name and id.

## [v1.9.3] - 02.09.2026

Review pass over the v1.9.0–v1.9.2 mail-guard work. Thirteen findings from a full review of the diff since v1.8.0, fixed by root cause rather than one by one: state changes that ran before the guard's verdict, fail-open rules that each path interpreted differently, a DNS check that could not tell "no such domain" from "resolver down", challenges that could be replayed, and a Turnstile driver that never actually worked under the admin CSP.

### Fixes
- **Guard refusals no longer leave state behind as if the mail had gone out.** A signup whose verification mail the guard refused had already been given a *new* verification hash (invalidating the link from the earlier mail); a queued study Email refused at send time stayed stuck in `status = sending` for the daemon to retry forever, and the synchronous (`use_queue = false`) path reported it as sent; a suppressed study owner produced no `survey_notifications` anchor, so the throttle never engaged and every recurrence re-hit the guard; a refused account self-test marked the SMTP credentials invalid. Now the hash is rotated only after a successful send (a brand-new account still gets its first hash up front, because the login page's "Resend link" identifies the account by that hash), a refused Email unit is marked `invalid_recipient` and the participant moves on with an `error_email_guard_refused` log line, a guard-refused admin notification anchors the throttle like a delivery would (a transient SMTP failure still does not), and an account test refused by the guard leaves the verified state alone.
- **Invite tokens are claimed atomically.** The invite was checked before and consumed after `User::register()`, so two concurrent signups with one token both passed the check, and a failed registration had already burned it. A single `UPDATE … WHERE used_at IS NULL` now takes the token out of circulation before the account exists (`used_by = 0` = in flight), a successful registration binds it to the new user id, and a failed one releases it. The duplicate-email check moved ahead of the claim as well, so an "already registered" answer no longer costs the invite.
- **One fail-open rule, stated once.** Missing guard tables let mail through (unchanged); a missing `survey_registration_invites` table now reads as "no usable invite" on every invite path — a grant must fail closed — instead of a 500 on some and an uncaught exception on others. Turnstile fails open only on transport failure, a 5xx, or an answer without a verdict; Cloudflare's own `"success": false` is final. The `forgot-password` form answers every outcome, including an unparseable address, with the same alert and redirect, so the guard cannot become an existence oracle by way of a different status code.
- **The Turnstile driver works under the admin CSP.** It emitted a plain `<script src>` for `api.js` — blocked by the nonce-only `script-src`, along with the widget's iframe and its calls home — and posted to `siteverify` with a hand-rolled cURL call that ignored the instance's outbound proxy settings. The widget now carries the request nonce, registers `https://challenges.cloudflare.com` for `script-src`/`frame-src`/`connect-src` on the one response that renders it (`Csp::allow()`, request-scoped), and verifies through `CURL::HttpRequest` with a 5 s budget. Browser-tested end to end with Cloudflare's test keys, alongside Altcha.
- **Altcha worked only on the first request of a session.** Both challenge drivers read the CSP nonce from `Site::getInstance()`, but `index.php` restores the `Site` from the session without registering it as that singleton, so on every later request the nonce they stamped on their inline script was not the one in the response header and the browser blocked it. For Altcha that inline module is what registers the self-hosted Argon2id worker: without it, the widget has no algorithm and reports "Verification failed" on every click — so anyone who visited the login page before "Sign up" (the normal route) could not register on v1.9.0–v1.9.2 with `challenge = 'altcha'`. The controller now hands its own nonce to `widgetHtml($cspNonce)`. Found by driving the widget in a real browser (`tests/e2e/registration-challenge.spec.js`, which runs against whichever driver the instance has configured and checks for CSP violations, a refused unsolved submission, and — for Altcha — a refused replay).
- **A second signup from the same browser session no longer dies with a 500.** A new account takes over the visitor's session code so surveys taken before signing up stay linked, but a second registration in that session (a typo'd address that never got its verification mail, say) reused the same code and hit `user_code_UNIQUE`. It now mints a fresh code when the session's already belongs to an account. Pre-existing, but the guard's refusals make a retry more likely.
- **DNS honesty.** The deliverability check treated SERVFAIL/timeout as "no records" (`checkdnsrr()` cannot tell the two apart) and cached that as an authoritative refusal for 24 h. It now uses `dns_get_record()` — `false` is transient and fails open uncached, an empty answer is authoritative — honours RFC 7505 null MX (`MX 0 .` = "never accepts mail"), keeps a control lookup for the resolver-answers-nothing case, and expires its per-process memo after 10 minutes so the long-lived mail daemon does not remember a verdict for the rest of its life.
- **Challenge responses are single-use.** An Altcha solution or a signed form timestamp could be replayed for its whole lifetime by anyone who captured one submission. Both are now burned in the session on first successful use, and the form timestamp is signed over the PHP session id as well, so a token minted in one browser is worthless in another. The honeypot treats `"0"` as a hit (`empty()` did not).

### Added
- **`mail_guard.log_retention_days`** (default 90; `0` keeps everything). The guard log and the domain cache were unbounded; the daily cleanup cron now prunes both, and patch 077 adds the `created` index that makes the sweep and the status page's time-window counts cheap.

### Schema
- Patch 077: `ADD INDEX IF NOT EXISTS idx_mail_guard_created` on `survey_mail_guard_log`. Additive, replayable.

## [v1.9.2] - 01.09.2026

People always want exceptions — this release gives superadmins an in-app lever for them.

### Added
- **Registration invites can be issued from the admin UI, and a valid invite overrides the domain gate.** New superadmin page `admin/advanced/registration_invites` (Advanced → Registration Invites): issue 1–50 single-use tokens with an optional expiry, see who issued/used each one, revoke unused ones. Tokens are displayed exactly once at issuance; only sha256 hashes are stored, and used invites are kept as an audit trail (who let whom in). In `domains` mode a valid invite now admits the one person carrying it past the domain/TLD restriction — the in-app answer to "my collaborator's email domain isn't on the list" that previously required host CLI access (`bin/registration_invite.php`, which remains and now shares the same implementation). The signup form shows the token field in `domains` mode, the rejection message mentions invitation tokens, an invite counts as a trusted signup (v1.9.1 rate-limit relaxation) in every mode, and a presented invite is burned on successful registration regardless of mode. `closed` still means closed — an operator wanting exceptions-only signup uses `invite` mode.

## [v1.9.1] - 01.09.2026

Follow-ups to the v1.9.0 mail-guard work.

### Fixes
- **Verifying an email no longer shows a contradictory "token invalid or outdated" error.** `User::setVerified()` wrote `email_verified = 1` and showed the success alert, then — in the same method — checked for a referral token to grant study-creation rights and, on not finding one, fired an `alert-danger` reading "Your email verification token was invalid or oudated", contradicting the success message a line earlier. This hit *every* plain signup without a referral token (the common case). Verification was never actually failing (the account is verified either way; `verifyEmailAction` ignores the return), so the branch now shows an informational note — "Your account is a participant account; ask an administrator for study-creation rights." — instead of a false error. Pre-existing since at least v1.8.0; not a v1.9.0 regression.

### Added
- **`registration.allowed_tlds`** — in `domains` mode, accept any address whose domain ends in one of these TLDs (e.g. `array('edu', 'ac.uk')`), so an instance can limit sign-ups to a whole TLD without listing every institution in `allowed_domains`. Same label-boundary suffix match (`edu` accepts `x.edu`, not `x.notedu.com`); the two lists combine.
- **Rate-limit relaxation for signups bearing a valid referral/invite token.** A spammer essentially never has one, so such signups now SKIP the per-IP and per-/24 ceilings — which otherwise blocked a workshop or course cohort all signing up from one institutional NAT — while remaining bounded by a separate, higher instance-wide ceiling (`mail_guard.trusted_global_limit_per_hour`, default 200) so a leaked token still can't bomb without limit, and by the unchanged duplicate-send / suppression / MX checks. The trust signal is a `referrer_codes` match (open/domains modes) or a usable single-use invite (invite mode); `RegistrationGuard::signupIsTrusted()` decides, and the flag rides the verification mail through `GuardedMailer`.

## [v1.9.0] - 31.08.2026

Outbound-mail abuse hardening. A hosted instance had its SMTP disabled after bots used the registration and forgot-password forms as a free mailer (subscription bombing). Every outbound message now passes a send-path guard (suppression, duplicate-send window, per-IP/subnet/global ceilings, MX plausibility, full attempt log), and registration gains gating plus honeypot/timing bot friction and an optional self-hosted Altcha challenge. Every default is chosen so an instance upgrading without editing its config keeps working.

### Added
- **Outbound mail passes through a guard before anything leaves the process.** Registration, resend-verification and password-reset mail previously went out through a bare PHPMailer with no log, no rate limit and no suppression support — so a bot submitting the signup or forgot-password form could use any open instance as a free mailer for subscription bombing, until the provider disabled SMTP for the whole mailbox (which is how this surfaced). All three mailer factories now hand back a `GuardedMailer` whose `send()` consults `MailGuardService`: every attempted handoff is recorded in `survey_mail_guard_log` (recipient, type, source IP, outcome — never bodies); suppressed addresses (`survey_mail_suppressions`, managed with `bin/suppression.php`) are refused on every path; unauthenticated *transactional* mail (verification, password reset) additionally gets a duplicate-send window (default 24h — which alone would have stopped the incident's repeat sends), per-IP / per-/24 / instance-wide hourly ceilings, and an MX/A plausibility check with a DB-backed cache that fails open when DNS itself is down and closed on an authoritative empty answer. Cron notices and study mail are exempt from the ceilings (many per hour is legitimate; study mail keeps its existing per-recipient `email_thresholds`) but share the suppression list, domain check and log. The guard fails open with a loud log line if its own tables are missing, so an upgrade ordered code-before-migration cannot break mail. A tripped global ceiling is flagged in the superadmin menu and on the new `admin/advanced/mail_guard` status page. Registration rejects over-limit requests with a clean 429 *before* creating the account; forgot-password answers refusals byte-identically to its success path so the guard cannot become an account-existence oracle. Covered by `tests/MailGuardServiceTest.php` (the SQLite lane runs the real queries — cutoffs are computed in PHP, not `DATE_SUB`, for exactly this reason) and `bin/test_mail_guard_smoke.php` (live MariaDB, including the choke-point wiring).
- **Registration gating and bot friction.** `registration.mode` = `open` (default, unchanged) | `domains` (allowlist of email domains, subdomains included) | `invite` (single-use tokens from `bin/registration_invite.php`, entered in the signup form's token field) | `closed`. The signup form always carries an invisible honeypot (hits mimic the success page and are logged) and an HMAC-signed timestamp (secret derived from the instance crypto key; too-fast or stale submissions are re-prompted) — on by default because neither can plausibly block a human. `registration.challenge` optionally adds a pluggable widget: `altcha` (self-hosted proof of work via the MIT `altcha-org/altcha` package and a webpack-copied, same-origin widget — no third party, no data-protection questions) or `turnstile` (Cloudflare; deliberately not the default since it ships visitor data to a third party). Drivers fail open on their own misconfiguration. Covered by `tests/RegistrationGuardTest.php`.

### Schema
- Patch 076: four new tables — `survey_mail_guard_log`, `survey_mail_suppressions`, `survey_registration_invites`, `survey_mail_domain_cache`. Purely additive (`CREATE TABLE IF NOT EXISTS`), replayable, no existing table touched.

## [v1.8.0] - 16.08.2026

Queue-hardening release. A three-angle audit of the RunUnit queue after v1.7.1 turned up eight defects; the seven verified against the code — and, where possible, against the live database — are fixed here. The common shape: a unit session reaches a state that neither the daemon pickup nor the recovery sweep can act on, so the participant silently stops progressing; or a delivery fails in a way nothing records. Plus one upstream feature.

### Added
- **A Skip unit's condition may return a position number, not just TRUE/FALSE** (upstream [#699](https://github.com/rubenarslan/formr.org/pull/699) by @timseidel). The number is an absolute run position to jump to, replacing the chain-of-skip-units idiom that complex routing used to require with a single unit. **The number must be 2 or higher: 0 and 1 always keep their boolean reading and can never be jump targets** (`Branch::MIN_COMPUTED_JUMP_POSITION`). R offers no boolean-vs-integer signal that survives the round trip — OpenCPU answers in JSON, so `TRUE`, `1L` and `1` all arrive as the same value — and conditions returning 1/0 are everywhere: `screener$consent` on a 1/0 coded item, `sum(x)`, `nrow(df)`, `as.numeric(...)`. Without the floor, every such skip written before this feature would have silently reversed on upgrade, and quietly: a run numbered 10/20/30 has no unit at position 1, so the invalid-target arm continues past the skip — precisely the arm the skip existed to avoid. Nothing is lost, since runs are numbered in tens and position 1 is virtually never a real destination; a run that does have one can be renumbered. Agreed with @timseidel before release. A computed jump is unconditional by design — it ignores `automatically_jump`/`automatically_go_on` and the cron gate, because there is no "wait for the user" semantics for a computed destination — and a target with no unit at that position notifies the study admin and continues rather than jumping into nothing. The admin Test view gains a "Routes to" column showing the real routing, so authors see where a participant would actually go instead of the raw R value — it and the live path now share one `computedJumpTarget()` decision rather than each implementing the rules, so the preview cannot drift from the behaviour it previews. A numeric condition also says which of the two readings applied in `result_log`, since that is exactly where an author can now be surprised — which required fixing the channel first: every terminal branch assigns `$data['log']` wholesale, so the warnings written earlier in the method were overwritten before they were ever logged. "Your R code is returning more than one result" and "is not returning true/false" have therefore been discarded silently for as long as this shape has existed; they are now folded into the terminal message and reach the row an admin reads. A clean TRUE/FALSE condition still records no log. Two supporting fixes in the same code: a nested R list no longer reaches `strtotime()` as an array, which was a PHP 8 TypeError that fataled `ajax_test_unit` — the whole Test view — over one participant's result; and the skip-unit help text and the public run documentation both state the 0/1 rule. Covered by `tests/BranchComputedJumpTest.php`.

- **`?_new_session=1` starts a fresh traversal** (merged from @timseidel's `feature/new-session-url-param`). A static link or QR code cannot embed a per-rater session code, so every scan resumed whichever session the browser's cookie happened to point at — useless for an external rating run scanned by many people, or one person rating several targets in turn. A GET on the run root carrying `?_new_session=1` now mints a fresh code and redirects to its `?code=` form, dropping the trigger so it fires exactly once and preserving any other query parameters (a target like `?rated=P1` survives into the survey's GET items). It runs before the PWA cookie self-heal, so a fresh code wins over resuming. It grants no new capability: the redirected request is still gated by `Run::exec()` on `(public >= 1 && already enrolled) || public >= 2`, the same bar a plain no-cookie visit clears, and the minted code is a full-entropy `crypto_token(48)` matching the configured 64-character code format. Two caveats worth knowing: on a `public >= 2` run every hit mints a run session, so anything following the link repeatedly (a crawler, a link previewer) creates them — a plain no-cookie visit already does this, and neither is rate-limited — and the change ships without a regression test, since controller-level session minting is awkward in the SQLite lane.

### Fixes
- **An empty R expression no longer evaluates to the string `"formr"` — and an empty Skip condition no longer jumps every time.** `opencpu_evaluate()` wraps the author's code in a closure that opens with `library(formr)`, so when the code contributes no expression — empty, whitespace, or comments only — the closure's value was that call's own return value, and R's `library()` returns the names of the attached packages. Evaluation therefore reported *success* with the string `"formr"` instead of failing. What that cost depended on the caller's coercion: `strtotime('formr')` is false, so a Pause/Wait anchor fell through to its `check_failed` path (noisy but safe), whereas Branch/Skip coerces with `(bool)` — and `(bool) 'formr'` is `TRUE`, so **an empty skip condition jumped on every evaluation**, silently, with nothing in the logs to explain the routing. An effectively-empty expression is now refused up front and returns `null`, which routes every caller into the "could not evaluate" handling it already has, with `opencpu_last_error()` explaining why (it gains a pre-flight channel, since a refusal never opens a session and would otherwise surface either nothing or a stale error from an earlier call). The classifier strips comments line by line, which can only make a string look emptier — real code always leaves non-comment characters behind (`x <- 1 # note`, `"#"`) — so it cannot refuse working code; `tests/OpenCpuEmptyCodeTest.php` pins both directions. The guard does not apply to the admin "Test" button, whose path expects a session object.
- **An oversized spreadsheet no longer kills the upload with an uncatchable memory fatal** (upstream [#700](https://github.com/rubenarslan/formr.org/pull/700)). When Excel leaves a formatted cell at the very bottom of a sheet, `getHighestDataRow()` reports its maximum of 1,048,576 rows; the row iterator, running with `setIterateOnlyExistingCells(false)`, then materialises a Cell object per row and column until PHP exhausts its memory limit. The fatal surfaces deep inside PhpSpreadsheet's `Coordinate.php` and no `try`/`catch` can reach it, so the only workable guard is to refuse before iteration begins: `SpreadsheetReader::MAX_DATA_ROWS` (50,000) now caps both the choices and survey sheets, with a message telling the author to delete the empty rows below their data and re-upload. Two things are fixed alongside: a failed choices sheet no longer lets `readSurveySheet()` run on and re-wrap the same error into a duplicate, misattributed "Error in cell B2 (Survey Sheet)"; and `readItemTableFile()`'s catch widens from `PhpSpreadsheet\Exception` to `\Throwable` so reader-internal `TypeError`s degrade gracefully too. This is the row-axis counterpart to v1.1.0's column-axis fix for the same class of bloat. Covered by `tests/SpreadsheetReaderRowCapTest.php`.
- **A failed email is retried instead of silently dropped.** Delivery was terminal after two immediate SMTP attempts: `sendEmail()` retried once in-process, wrote `STATUS_FAILED_TO_SEND (-2)`, and the pickup poll only ever selected `status = 0` — so nothing looked at the row again. No re-arm, no notification, and the unit session had already reported `email_queued` and advanced the run, so a 30-second SMTP blip lost a study's email with no trace beyond a debug line. The tell was `queue_item_ttl` / `queue_item_tries`: read into properties at construction and used nowhere — the signature of a retry that was designed and never connected. `-2` now means "failed, possibly retryable": the poll re-selects while `tries` is under budget and `last_attempt` has aged out, one try is spent per queue pass (before the send, so a row that kills the daemon burns budget rather than retrying forever), and giving up becomes deliberate — recording `result='email_gave_up'` with the last SMTP error on the unit session, where the user-detail table and its CSV export already surface it. Rows that failed under the *old* semantics are retired on migration rather than swept into the new retry arm: both columns land on existing rows at their defaults (`tries = 0`, `last_attempt` NULL), which matches the retry predicate exactly, so on an install with any delivery history the first daemon pass after upgrading would have re-delivered every email that ever failed — SMTP blips, dead addresses, studies closed years ago. (The TTL check would not have caught it: `isGivingUp()` runs *after* `$mailer->send()`, so it can stop the second attempt but never the first.) `last_attempt IS NULL` identifies the historic rows precisely — `countAttempt()` stamps it before every SMTP try, and `sendEmail()` is the only writer of `-2` — so rows that failed under the new code keep their real budget. **Schema:** patch 071 adds `tries` + `last_attempt` to `survey_email_log`; patch 072 backfills the pre-migration failures to an exhausted budget.
- **An email skipped because the participant switched emails off no longer parks the run.** The branch returned log+content only, and `executeUnitSession()` returns content as the page body *before* reaching its fall-through `moveOn()`, so the row stayed at `queued=0` — invisible to the daemon pickup. On the web path the participant hit a dead-end page; on a cron cascade nothing rescheduled it, so every snoozed or opted-out participant parked on their Email unit until the stalled-session sweep healed it (~30–100 minutes). It now ends and advances, like the `cron_only` skip beside it — which only worked because it sets no `content` and so reaches the final `moveOn()`.
- **A skip unit whose condition fails to evaluate no longer hammers OpenCPU.** `Branch::getUnitSessionExpirationData()` (inherited by SkipForward/SkipBackward) set `wait_opencpu` but not `check_failed` on both halt paths — the OpenCPU error and the F9 dangling-jump-target guard — so `UnitSession::isExpired()`'s F19 backoff never re-armed the row. Pause sets `check_failed` on the identical failure; the asymmetry meant an already-queued skip unit kept its past deadline and was re-picked on *every* daemon pass: roughly 5,760 OpenCPU evaluations a day, and an admin error mail every throttle window, for a single stuck participant. Both paths now flag it, so the row backs off and picks up the admin's fix at the next retry.
- **An External whose R address fails to evaluate is retried instead of stranded.** It set `wait_opencpu` and returned, leaving the row inert at `queued=0` — and External is precisely the type the stalled-session sweep skips, on the reasoning that an External waits for a callback or for the participant's browser. That holds for `api_end` and address externals, but not for one whose R address failed to evaluate: it waits for neither. The participant parked there indefinitely unless the run set `expire_after`, and the R side-effect — an SMS, an API call — silently never happened. It now re-arms on the standard backoff, and — importantly — the retry *terminates*: the success path used to set `redirect` and nothing else, while `executeUnitSession()` returns at its `formr_in_console()` guard (a cron cascade must not follow a redirect) before touching the queue, so a row re-armed at `QUEUED_TO_EXECUTE` kept a past-due `expires` once OpenCPU recovered and was re-executed on *every* daemon pass — re-firing the address's side effect every ~15 seconds for as long as the participant sat there. A cron pass that produces a redirect now hands the queue this unit's ordinary expiry verdict instead: `expire_after` re-arms `QUEUED_TO_END` (which routes the next pickup through `revalidateQueueVerdict()` and terminates), no `expire_after` dequeues. The participant still gets the redirect on their next visit. Covered by `tests/ExternalCronRequeueTest.php`.
- **The API v1 `advance` action takes the run-session lock.** It was the last caller driving `endCurrentUnitSession()` + `moveOn()` by hand without it (the F3 class, fixed for the admin AJAX path but missed here). Racing a daemon cascade, both sides could end and advance from a stale position, duplicating downstream unit sessions and re-sending their emails and pushes. It now goes through `forceMoveOn()`, which takes the lock, re-reads the session inside it, and refuses on an already-ended run session. **Behaviour note:** the advanced unit session is recorded as ended with `result='moved'` where the old path `expire()`d a Survey/Form/External — the more accurate label for an operator-forced advance, and consistent with what the admin UI records for the same action.
- **The legacy v0 `end-last-external` API callback works again.** It passed `null` to `RunSession`'s non-nullable `Run $run`, raising a TypeError that `ApiController`'s `Throwable` catch turned into a JSON 500 — on every call, so the endpoint was not merely buggy but permanently broken. Any external service still using it could never end an `api_end` External, leaving the participant parked until `expire_after`, or forever where that is unset. It now passes the run it had already validated. **It was broken twice**, and the second break hid behind the first: `ApiController::doAction()` resolved OAuth token data unconditionally, but `authenticate()` deliberately builds no OAuth server for `$unrestrictedActions` — and this endpoint is the only member of that list — so every call died on `Call to a member function getAccessTokenData() on null` one line *before* `ApiV0` was constructed, and the same `Throwable` catch produced the same JSON 500. Fixing only the TypeError would therefore have changed nothing observable, which is why the second defect survived a fix aimed at the first. Token data is now resolved only when there is a token, and `ApiBase` returns early on a null one rather than dereferencing it: an unrestricted action has no user to hydrate and no grant to re-check, so the defence-in-depth `canAccessApi()` check that guards every authenticated endpoint is untouched. `end-last-external` authorises on its own terms, by the participant's session code — the same secret a run URL's `?code=` carries. Found by the new browser coverage lane, which drives the callback the way an external service does: the participant is redirected out carrying `{{login_code}}`, the service posts back, and the row must read `external_ended` (`tests/e2e/result-coverage-external.spec.js`).
- **A push notification whose message or title fails to parse now tells someone.** Both branches are terminal — the claim is resolved and the run advances — which is defensible for genuinely broken content but not for a transient OpenCPU failure, which produces an identical falsy parse result. The drop is now reported to the study admin instead of happening in silence. Retrying is deliberately *not* added: push delivery is not freely retryable, because iOS terminates a subscription after roughly three pushes it considers silent, so a retry loop on a permanently-broken message would cost the participant their subscription entirely — worse than the dropped prompt. Doing it properly needs a bounded, persisted attempt budget (like `survey_email_log.tries` above) plus a transient-vs-permanent signal from the parse step.

- **A service-worker install no longer advances the participant's run.** Found while investigating the field report that a Wait after a PushMessage ends by itself, and the leading candidate for that report's cause — though not proven for that specific incident. A controlled experiment on the dev instance settled the mechanism: driven by the daemon alone, with zero HTTP requests, every Wait configuration parked for its full `wait_minutes` and then advanced normally; adding a **single** GET on the run URL produced the early end and the jump to `body` every time, and did so whether the `relative to` field was empty or held a valid expression. So the trigger is *any* HTTP request touching the run while a Wait is parked — `Wait::getUnitSessionOutput`'s early-return branch reduces to `!isExecutedByCron()`, because a parked Wait satisfies its other two conditions by definition — and this defect supplied exactly that stimulus, unprompted, on every service-worker install. The service worker's `install` handler precached `[manifest.start_url, …icons]`, and `safeAddAll` fetches every entry with `credentials: 'same-origin'` — but `start_url` is not a static asset. `RunController::personalizeManifest` sets it to the participant's own run URL *with their session code*, confirmed live (`…/<run>/?code=<participant code>`). So every install fired an authenticated GET on that participant's run, which is `RunController::indexAction` → `RunSession::execute()` in a **web** context, since `isCron()` is purely `$user->cron` and only the queue sets it. A parked Wait then saw `!isExecutedByCron()`, took its "participant came back early" branch and jumped to `body`. The reporter's logs show exactly that: one run went from position 50 straight to 80, skipping 60 and 70 — `run_to = body`, not `move_on`. No interaction is needed, which is why they were never back in the app; the correlation with pushes is the worker lifecycle, since a push wakes the SW and `skipWaiting()` installs the new one, so the install fetch lands within a second of the push. Wait was merely where it was visible — the same GET also stamped activity, created unit sessions and rendered surveys unbidden. Nothing is lost by dropping `start_url` from the precache: the fetch handler only serves URLs passing `isValidUrl()` (paths containing `/assets/` or `/manifest`), which the run URL matches neither, so the cached response could never be read. `sw_version` goes v7 → v8 so installed PWAs pick this up and the v7 cache holding that response is evicted.
- **A Wait that a participant returned to early is distinguishable from one that elapsed again.** `UnitSession::end()` derives the result from the unit *type*, writing `wait_ended` for any Wait it ends and overwriting what the unit's own log just recorded — so both exits of `Wait::getUnitSessionOutput()` read `wait_ended` in the results table. The collapse arrived in v1.7.1: removing the leaked `expired` flag correctly routed an elapsed Wait through `end()` instead of `expire()`, so the elapsed case stopped recording `expired` and started recording `wait_ended`, the label the early-return branch had always produced. Two outcomes, one label, and no way to tell a healthy timeout from a premature advance without reading `state_log`. Units can now name their own terminal result: Wait's early-return branch sets `end_reason='wait_ended_by_user'` and `executeUnitSession` passes it to `end()`, which has honoured an explicit `$reason` since the queue's `ended_by_queue_rse` work. Units that set no `end_reason` are unaffected, so the elapsed case keeps `wait_ended`.
- **An early-ended Wait records which kind of request ended it.** The early-return branch fires for *any* non-cron execution, so its log line now carries the request's `Sec-Fetch-Dest`/`Sec-Fetch-Mode` — browser-set headers that scripts cannot forge. `document`/`navigate` is a real navigation; `empty`/`cors` is something fetching the run URL programmatically, which is what the service worker used to do. Purely diagnostic: nothing branches on it, deliberately, because the headers are absent on older browsers and on non-browser clients, so any policy built on them could only fail open. If an unattended executor reappears, this names it instead of leaving the whole chain to be re-derived. The values are attacker-controlled headers landing in `result_log`, which admin templates render without auto-escaping, so they are whitelisted to the spec's token characters and length-bounded (covered by a test).

- **`result` and `result_log` are now a matched pair, and a unit's own verdict survives.** `UnitSession::end()` re-derived the result from the unit TYPE alone, so whatever the unit had just logged was overwritten: a Survey that recorded `survey_completed` ended as `survey_ended`, an External that recorded `external_r_call_no_redirect` as `external_ended`, a Pause that recorded `error_pause_relative_to` as `pause_ended`. Distinct outcomes collapsed into one label — which is why an admin force-push through `forceTo()` was indistinguishable in the results table from a genuine survey completion. Meanwhile `result_log` was re-written verbatim from the value `load()` had hydrated out of an *earlier* pass, so a row could carry a label describing one event beside text describing another (`pause_ended` next to an OpenCPU traceback, a skip `moved` next to an R error) — worse than no text, because it sends whoever reads it after the wrong bug. `resolveEndResult()` sets the precedence to explicit caller reason → this pass's own log → type default, and clears the log whenever the result did not come from this pass. Wait's v1.8.0 `end_reason` lever becomes the general case rather than a per-unit workaround; units that record nothing keep their type default exactly as before. **Analysis note:** a completed Survey now records `result='survey_completed'`, not `survey_ended`. That is the point of the change — previously a genuine completion and an admin force-push both read `survey_ended`, which is exactly how `forceTo()` came to manufacture false completions — but any query counting completions by `result='survey_ended'` must be updated. `survey_ended` now means only "ended without the unit recording a verdict": a forced advance, or a queue-driven end. Covered by `tests/EndResultPairingTest.php`. Found by a per-unit audit of this defect class across every RunUnit — see `documentation/agent_doc/LOG_STATE_AUDIT.md` for the full findings, including the ones not fixed here.

- **An admin force-move no longer counts as a survey completion, and finally records itself (audit X1).** `RunSession::forceTo()` — the "send this user to that position" button, and `positionSessions()` in bulk — called `UnitSession::end()` and only then assigned `manual_admin_push` and called `logResult()`, whose `AND ended IS NULL` guard matched zero rows. The label had **never once existed in the database**, for any unit type, so a forced advance was indistinguishable from the unit ending on its own. The costly half was elsewhere: `end()` on a Survey also stamps the results row's `ended` and fires `StudyMetrics::recordCompletion()`, and `ended IS NOT NULL` is the standard completion filter in analysis — so moving someone parked mid-survey manufactured a row that counts as a finisher and folded a non-completion into the study's geometric-mean duration. The rollup is an accumulator, so the skew was permanent, silent, and reached published numbers. `end()` now takes a `$completes` flag that the two operator paths (`forceTo`, `forceMoveOn`) set false, and the reason is passed *into* `end()` so `resolveEndResult()` gives it precedence. **This could not be fixed before X2 below**: passing a reason overwrites `result`, which for a Shuffle was the API's only copy of the group assignment. Catalogue note: `manual_admin_push` moves from unreachable to admin-reachable. Covered by `tests/e2e/result-coverage-admin.spec.js`, which asserts both the label and the results row staying unfinished.
- **The API and the admin no longer disagree about which group a participant is in (audit X2).** `ApiBase::getShuffleResults()` selected `sus.result AS group`, so the v1 API reported the string in `survey_unit_sessions.result` while the admin's randomisation page, its CSV/XLSX exports and the author's own `shuffle$group` in R all read `shuffle`.`group` — two copies of one fact in two value spaces (`'group_2'` against `2`), with nothing keeping them in sync. And the API's copy was the wholesale-overwrite column: anything writing another reason into `result` before the participant returned made the API report `group: "moved"` for someone whose R still read `2`, silently mis-assigning them in any analysis that joined on the API's answer. The query now reads the authoritative column and formats it as `group_N`, so existing clients see exactly the value they always did and only the source moved; a legacy row whose shuffle entry predates the table still falls back to its old `result`. Covered by `tests/e2e/result-coverage-shuffle-api.spec.js`.
- **Two audit findings closed by testing rather than by reading.** `no_sender` and the SMTP give-up path had both been described as unreachable-in-practice; driving them showed why, and neither reason was the one in the notes. An Email's sending account cannot be left unset by an author who *has* an account — `Email::changeSettings()` substitutes the first of `Site::getCurrentUser()->getEmailAccounts()` — so `no_sender` belongs to the first day of a study, before anyone has configured SMTP, and is now covered by a fixture owned by an account with none. And a *deliberately* broken email account can never be picked up at all: the daemon polls `survey_email_accounts.status = 1`, status 1 comes only from `EmailAccount::test()` succeeding, and every save resets it to 0 — so the v1.8.0 give-up path can only ever fire for an account that broke *after* being verified (host moved, credentials rotated, server down). That is now reproduced honestly, by pointing the account's host at 127.0.0.1 inside the mail daemon's container, with `docker restart` as the revert since it regenerates `/etc/hosts`.
- **A push notification to a run without VAPID keys no longer fatals the request.** `PushNotificationService::getVapidPrivateKey()` read `survey_runs.vapid_private_key` and handed it straight to `Crypto::decrypt()`, whose parameter is typed `string`. On a run that never generated a PWA manifest that column is NULL, so the call raised a **TypeError — an `Error`, not an `Exception`**, and PHP 8's type system turned an ordinary authoring mistake into an uncatchable one: it blew past the constructor's own `VAPID keys not found` guard three lines further down, past `PushMessage`'s `catch (Exception)`, past `RunSession::execute()`'s `finally`, and past `UnitSessionQueue::run()`'s `catch (Exception)`. The participant got a 500, the unit session was left with `result = NULL` — a push failure that erased its own record, which is precisely the defect class this release set out to close — and the run daemon met the same row on its next pass, the crash-loop shape already seen with the Branch nested-list TypeError. Adding a PushMessage to a run before generating its manifest is a normal thing to do while building a study. The getter now returns null for an empty key, so the existing guard fires: a catchable exception, `result='error'` naming the cause, and a run that keeps moving. Found by the browser coverage lane while chasing the one audit finding left open in `LOG_STATE_AUDIT.md` ("PushMessage `error` writes no row at all"), which this confirms and closes. Covered by `tests/e2e/result-coverage-push.spec.js`.
- **Removing a unit from a run no longer deletes participants' history for it.** Six of the nine unit types — Page/Endpage, Pause, External, Branch, SkipForward, SkipBackward and Shuffle — overrode `removeFromRun()` with `return $this->delete($special)`, and `delete()` drops the `survey_units` row itself. `survey_unit_sessions.unit_id` is a foreign key **ON DELETE CASCADE**, so deleting one of those units from the run editor silently removed every participant's unit session for it: every result, every log line, every timestamp of who reached it and what happened there. An admin tidying a run destroyed the rows they might have been reading a moment earlier, with no warning and no trace — the deletion confirmation warns about the unit, not about the data. This is a strictly worse failure than the one the v0.26 audit fixed for the other three types (F22/F7), where an unlinked placement merely left in-flight sessions dangling; and the two types most likely to be deleted mid-study, Pause and Endpage, were both in the unprotected set. The overrides now delegate to the base `removeFromRun()`, which ends live sessions at the placement (recording `unit_removed_from_run`) and then deletes only the `survey_run_units` link, leaving the unit definition orphaned but the history intact — the admin UI already has a path for orphaned units. Found by the new browser coverage lane: its fixture deletes an Endpage and expects the parked row to carry `unit_removed_from_run`; the row was not unstamped, it had ceased to exist. Covered by `tests/e2e/result-coverage-structure.spec.js`.
- **An imported run no longer turns every Email into a cron-only one.** `Email::changeSettings()` computed `cron_only` as `(int) isset($options['cron_only'])` — the field's *presence*, not its value. That is right for the admin form, where an unticked checkbox simply is not posted, and wrong for every caller that sends the field explicitly: the v1 API, a run import, the MCP. `cron_only: 0` arrived as 1. And since `cron_only` is in `$export_attribs`, the round trip was lossy in the worst direction — **export a run, import it back, and every Email in it became cron-only**, after which a participant who reached one in their browser was skipped with `email_skipped_user_active` and never mailed, while the same run kept working for anyone the daemon drove. Sharing or restoring a run from its own export was enough to trigger it. Absence still means 0, so the admin form behaves exactly as before. Found by the new browser coverage lane: seven Email fixtures built through the MCP with `cron_only: 0` all recorded `email_skipped_user_active`.
- **An OpenCPU error email now describes the failure it reports (audit X3).** `opencpu_last_error()` had two ways to hand the study admin someone else's diagnosis. The `$GLOBALS['opencpu_local_error']` note added with the empty-expression guard was cleared only by `opencpu_evaluate()`, so in a long-lived daemon process a note left by one participant's comments-only Skip condition was reported as the explanation for a later, unrelated knit failure — a different unit, possibly a different participant, told "The R expression is empty" about an expression that wasn't. And a transport failure (OpenCPU down, 502, timeout) constructs no session at all, so the fallback read the *previous* session — whose `hasError()` consults the singleton's just-overwritten `curl_info`, returning the body of an earlier successful call as the "error", or nothing ("…knitting page content. " with no detail). Every knit wrapper now clears the note on entry, so it cannot outlive the call it describes, and a transport failure leaves its own note (`OpenCPU request failed: …`, secrets redacted) — every outcome of every wrapper yields an accurate `opencpu_last_error()`. Covered by `tests/OpenCPULastErrorTest.php`, red pre-fix on all three staleness paths, driven against a connection-refused OpenCPU so no network or timeout is involved.
- **Admin error notifications are throttled per unit, not per run — and what the throttle swallows leaves a trace (audit X4).** `Notification::canBeSent` keyed its 10-minute window on run + recipient + type, so every error source in a run shared one email slot: during an incident the admin heard about whichever unit failed first, and every *distinct* problem in the window was dropped — without record, since only delivered notifications were logged, leaving silence indistinguishable from health. The throttle now keys on a per-unit fingerprint (`<type>:u<unit id>`): a repeat of the same unit's problem stays throttled, a different unit's problem gets its own email. Suppressed notifications are recorded in `survey_notifications` (`suppressed = 1`; they do not restart the window), and the next delivered email carries a digest ("N similar notifications about this unit were suppressed by throttling since the last email."). The interactive-testing mute moved out of `canBeSent` into `notifyStudyAdmin`: a preview error is muted by design, not throttled, so it writes no suppression row. The OpenCPU-down branch of `getParsedBody()` also gains its own channel: it now notifies the study admin with the unit's type, position and the accurate transport error, for **every** unit type — previously only Page had one, via a duplicate notify in `getUnitSessionOutput()` that in the R-error case fired microseconds after `getParsedBody`'s own and was always throttled away, and in the down case was built from the stale global X3 describes. That duplicate is removed. Covered by `tests/NotificationThrottleTest.php` and `tests/OpenCPUDownAdminNotifyTest.php`, both red pre-fix. **Schema:** patch 075.
- **The run menu's "Old Guinea Pigs" link finds guinea pigs again.** It pointed at `user_overview?session=XXX` and depended on the session search being a *substring* match: test codes are `<animalname>XXX<token>`, so `XXX` never occurs at the start. v1.7.1's slow-query pass dropped the leading wildcard so that search could use the index on `session` — correct for the search box, but it silently turned this link into "codes beginning with XXX", which matches nothing on any run, with no error to explain the empty table. The view now filters on `survey_run_sessions.testing`, the flag `getTestSession()` sets and the stethoscope button toggles, through a new `testing` parameter. It is surfaced in the search form as a three-way **Everyone / Guinea pigs only / Real users only** control rather than left as invisible URL state, so an admin arriving from the menu can see which filter is on and switch it off. One behaviour change: `getNamedSession()` also appends `XXX` to *named real* sessions, so the old link listed those alongside the test ones; they are participants rather than guinea pigs and no longer appear here (they are under "Real users only", with everyone else). **Schema:** patch 074 adds `(run_id, testing, last_access)` — the filter is then a single range scan that also satisfies the `last_access DESC` sort, where otherwise finding a run's few test sessions means walking all of its sessions (on the dev instance's largest run: 1 among 104,872).

### Removed
- **The `state_log` column is gone** (patch 073). Added in v0.26.0 as a structured JSON sibling of `result_log`, it acquired eight writers and no production reader: no admin template selected it, the v1 API projected `state` but not `state_log` (despite its own docblock telling clients to debug via `state_log`), and the property `load()` hydrated was never read — the only consumer in the tree was the smoke test asserting the write it had just made. Nor did it hold anything the row didn't: `reason` was derived from `result`, `ctx.unit_type` from the unit, `ctx.msg` was a copy of `result_log`, and `at` was rewritten wholesale every pass. It cost more than nothing, too — being a third thing to keep in sync it drifted (`giveUp()` wrote `result` without it; the supersede UPDATE and `addItem()` wrote `state` without it), and the reverted v1.7.1 streak-marker rework stored its marker there, in a column `logResult()` overwrites on every pass. The `state` ENUM is kept; it has real readers. **Schema:** patch 073 drops the column — guarded with `DROP COLUMN IF EXISTS`, because the same commit removed it from `sql/schema.sql` and so a fresh install never has one to drop, which is also the state the migrations CI replays patches against (it seeds `schema.sql`, baselines at the highest patch on the base branch, and applies only what the PR adds — without the guard that replay failed with errno 1091).

### Schema
- Patch 071 — `survey_email_log` gains `tries` + `last_attempt` and the `idx_status_retry` index (the email retry budget; see Fixes). Both are also folded into `sql/schema.sql`, and the patch is guarded with `IF NOT EXISTS` so the migrations-CI replay against the reconciled schema succeeds.
- Patch 072 — one-shot backfill retiring pre-migration failed emails (`tries = 255` sentinel) so the new retry arm cannot re-deliver years-old failures (see Fixes).
- Patch 073 — drops `survey_unit_sessions.state_log` (see Removed).
- Patch 074 — adds the `(run_id, testing, last_access)` index on `survey_run_sessions` for the guinea-pig filter (see Fixes); also folded into `sql/schema.sql`.
- Patch 075 — `survey_notifications` gains `fingerprint` + `suppressed` and the `(run_id, recipient_id, fingerprint)` index (per-unit notification throttle with suppression records; see Fixes). Also folded into `sql/schema.sql`, and guarded with `IF NOT EXISTS` so the migrations-CI replay against the reconciled schema succeeds. Legacy rows keep a NULL fingerprint and are no longer consulted by the throttle, so at most one extra email per unit can go out in the first window after upgrading.
- Patch 066 (retroactive) — every `DROP INDEX` gains `IF EXISTS` and the `oauth_scopes` PK addition gains `IF NOT EXISTS`, so the patch replays cleanly against a schema where a key is already gone (or was never present) instead of failing with errno 1091. Same replay convention as 071/073/075; the ENGINE conversions were already idempotent.

### Known gaps (tracked, not fixed here)
- Queued emails whose sending account is later deactivated or deleted sit at `status = 0` indefinitely: the pickup poll's `survey_email_accounts.status = 1` join hides them, so they never reach the new give-up path either.
- The email retry tier is flat (`unit_session.queue_expiration_extension`, default +10 minutes), not the escalating and capped backoff Pause and skip units get from `UnitSession::recheckBackoffExpression()`. Sharing that mechanism needs the streak-keyed rework deferred from v1.7.1, which in turn needs a column `logResult()` does not overwrite.
- The queue daemons have no per-item exception isolation: one poison row — a corrupt account `auth_key` failing `Crypto::decrypt`, say — throws out of the whole loop, and the restart meets the same row again, halting delivery for every account.
- Push retry (above), and the transient-vs-permanent classification `PushMessage` currently flattens into a single `error` result.
- **Any HTTP request against a run advances a parked Wait, and the sources are not all known.** A 2×2 experiment on the dev instance (empty vs. valid `relative to`, after a PushMessage vs. not, daemon-only vs. one GET) showed the `relative to` field is irrelevant: daemon-only, every arm parked and advanced correctly; one GET, every arm ended early and jumped to `body`. The branch reduces to `!isExecutedByCron()`, since a parked Wait satisfies `expired == false` and `check_failed == false` by definition. Removing the service worker's `start_url` precache (above) eliminates the one confirmed unprompted source, but a push-notification click, tab restore, link prefetch, or an uptime scanner hitting the run URL would each do the same, and none is distinguishable from a participant returning. The request-shape logging above exists to identify the next one from data.
- **`Wait::setDefaultRelativeTo()` is dead code.** It guards on `$this->has_wait_minutes && !$this->has_relative_to`, but those flags are set only by `parseRelativeTo()`, which runs *after* it and itself substitutes the default in exactly that case. Harmless today — the substitution still happens — but it means a Wait with `wait_minutes` never anchors on the previous unit session as the method intends, and the `tail(survey_unit_sessions$created,1)` literal it falls back to is then short-circuited to `$unitSession->created` without any OpenCPU call. Removing the service worker's `start_url` precache removes the only known unattended caller, and the new request-shape logging exists to catch another if one appears; gating the branch on `Sec-Fetch-Dest: document` was considered and rejected for now, since a `document` navigation can itself be automatic (`clients.openWindow()`, tab restore, prerender) and the headers' absence on older browsers means such a rule could only ever fail open.

## [v1.7.1] - 09.08.2026

Ports the fixes from Tim Seidel's upstream reports ([#702](https://github.com/rubenarslan/formr.org/pull/702), [#703](https://github.com/rubenarslan/formr.org/pull/703)) that this line had not already fixed independently — #702's first fix, hydrating the current unit session through `load()` in `RunSession::getCurrentUnitSession()`, landed here in v1.5.0 (`8db87c39`) — plus fixes for four defects found by auditing the same seams those reports exposed: places where a hardening pass added a guard, an allowlist or a rewritten query and quietly changed behaviour nobody re-checked. A follow-up code review of this branch then hardened the first cut of two of them (the fan-out fallback and the elapsed-Pause leak both missed an edge; the Google-Sheet re-link opened an XSS that is now closed — details in each entry), and a fifth audit fix — a rework of the Pause/Branch recheck backoff — was **attempted and reverted**: it could not work without a schema change (see below). No schema changes; no migration.

### Fixes
- **Every data frame handed to R is now returned in chronological order.** `UnitSession::getRunData()` built its queries with no `ORDER BY` at all, so `tail(survey_unit_sessions$created, 1)` — and every other last-row idiom in study-authored R (`relative_to`, Branch conditions, item `value`/`showif`, email bodies) — did not mean "the most recent row". The optimizer drives from `survey_run_units` and does a per-unit ref lookup, so rows came back grouped by unit and `tail()` reliably returned the newest session of *whichever unit sorts last*; a unit only visited on a rarely-taken branch goes stale while the participant loops, and the error grows with the participant's history. Measured on a dev participant with 1805 unit sessions, through the real PHP path: `tail(created, 1)` returned a timestamp **17 hours** older than the true latest. `created` is now the sort key (it is what `tail()` is being asked for) with `id` as tie-break — ties are real, since a cascade creates several unit sessions inside the same second. The two frames with no unit sessions in scope (`survey_run_sessions`, `survey_users`, both single-row per participant) are unordered as before. Index-served by `idx_run_session_created_id`; the sort set is one participant's history, not the table. Upstream this was half of the Wait premature-expiry fix — that symptom does not reproduce on this line, because v1.5.0's hydration fix plus the local anchor short-circuit in `Pause::getUnitSessionExpirationData()` keep the engine's own Wait anchor off the OpenCPU path entirely; what it fixes here is study-authored R.
- **A Pause/Wait that simply elapsed is no longer recorded as `result='expired'`.** Pause's recompute path assigns `end_session` and `expired` the same value, and `isExpired()` merged the whole payload into `execResults` before returning through its own `// ended NOT expired` branch — so the `expired` flag rode along, and `RunSession::executeUnitSession()`, which tests `expired` before `end_session`, called `expire()` instead of `end()`. The branch taken was identical either way (`move_on`), but the row was stamped `expired` with `ended` left NULL, so `result` alone could not distinguish a healthy elapse from a miscomputed deadline — and that NULL `ended` is what fed the wrong `seconds_stayed` in the export below. v1.7.0 had already closed the two sibling paths (the stored-deadline `QUEUED_TO_END` return, and audit F23's recompute branch); this closes the third. The flag stays set in the expiration payload itself, because `Wait::getUnitSessionOutput()` branches on it to tell "participant returned in time" from "wait elapsed" — only the copy leaking into `execResults` was wrong. The strip runs before every return path in `isExpired()` (whenever `end_session` is present), because a text-only Pause — or one whose boolean `relative_to` yields true — hands back `end_session`+`expired` with **no** `expires`, and so returns at the empty-`expires` guard that the first cut's unset sat after; the code review caught that fourth path. Regression test `tests/PauseElapsedNotExpiredTest.php` (both paths red pre-fix), which also pins that a genuinely lapsed Survey/External access window still expires.
- **User-detail export: `seconds_stayed` was wrong for every expired unit session, and four columns from the web view were missing.** The column was `IF(ended > 0, ended - created, NOW() - created)`, and a session that *expired* rather than *ended* has `ended` NULL — so every expired row took the `NOW()` branch and reported "time since the participant entered this unit, as of the moment you clicked Export" instead of a duration. The number grew on every re-export of the same session and contradicted the admin web view, which renders the raw timestamps. It hit exactly the rows an export gets pulled to investigate: Survey inactivity expiry and elapsed Pause/Wait units. Confirmed on live data — a session that expired after 3607 s exported as 100424 s. It now falls back to `expired` before `NOW()`, so `NOW()` applies only to sessions still genuinely open; rows with `ended` set are unaffected. Additionally `expires`, `queued`, `result` and `result_log` are appended **after** the existing nine columns (so positional parsers of the old format keep working): the export carried only `created`/`ended`/`expired` while `templates/admin/run/user_detail.php` also renders the computed deadline and the result, and without `expires` an export showing a 10-minute Wait that ended after 1 second gives no way to tell a miscomputed deadline from a correct one being ignored.

- **A unit slotted at several positions no longer multiplies its unit sessions across the admin tables, the exports and the API.** Eight queries paired a unit session with its run placement by joining `survey_run_units` on `unit_id`, which keys on the unit *definition* rather than on the placement — so every session of a unit that appears at N positions came back N times, each copy carrying a different `position`. The user-detail table and its export, the push-message log, the randomization table, the run data export and two API endpoints were all affected; on this dev instance's oldest run that was 4883 phantom rows out of 22108 (22%). The v1 unit-sessions API endpoint had it worst, because the duplication happens *before* `LIMIT/OFFSET`: duplicates consumed page slots, so a paginating client silently lost real rows it would never see on any page. All eight now resolve the placement through `survey_unit_sessions.run_unit_id` (patch 047, an indexed PK lookup) with a fallback arm for rows predating it — and that fallback pins to a single placement rather than matching them all, because for a legacy row the true placement is unknowable and these are row-per-session views: a best-effort position on one row beats N wrong rows. This matters more than it sounds — 26% of the unit sessions on that run still carry a NULL `run_unit_id`, so without the pick the fix would only have helped sessions created after patch 047. `RunMetrics::reconcileRunMetrics`' `n_unit_sessions` rollup moves in lockstep, since v1.7.0 had deliberately made it fan out the same way to keep the page count matching the rows shown; upgrading instances pick the corrected value up at the next nightly reconcile, and until then an over-count only shows a short trailing page. Verified per run against the live database: counts are unchanged for every run without a multi-position unit, and exactly equal to the distinct-session count for those with one. Regression test in `tests/UnitSessionResourceTest.php` (red pre-fix: 6 rows where 4 sessions exist). **Known limitation** (flagged by the code review): for legacy rows (`run_unit_id` NULL) the single-placement pin resolves a multi-position unit's sessions to the *lowest* position, so a user-detail **position filter** for one of the other positions will miss those legacy sessions, and unfiltered views label them with the pinned position. v1.7.0's fan-out was also wrong here but always emitted one row bearing the true position, so a filter still found it. The tradeoff is deliberate for the row-per-session views (a best-effort position beats N duplicates); a precise fix — flagging fallback-resolved positions as approximate — is tracked for `feature/form_v2`.
- **A survey no longer expires early because its inactivity clock read the wrong row.** `Survey::getUnitSessionLastVisit()` projects `COALESCE(saved, created)` — "when was this participant last active here, falling back to render time" — but sorted by the raw, nullable `saved` and only then by `created`. In `DESC` a NULL `saved` sorts *last*, so an item rendered after the participant's most recent save — i.e. the page they are looking at right now — could never win, and the function returned the older save instead. That value anchors the inactivity-grace branch of per-unit expiry, so the deadline was computed from a stale timestamp and a session could expire while the participant was still working, by up to one page's think time. Now sorts by the same expression it projects, with `id` as tie-break (`createSurveyStudyRecord` stamps `created` identically for every item of a page). The sort needs `DB::raw()` — the strict-identifier validation added to `DB_Select::order()` in v0.26.x rejects expressions, which is why the mismatch could not simply be written correctly at the time.
- **A failed email no longer spins the daemon at full speed.** A send failure correctly returns neither `end_session` nor `move_on` — the participant must not be advanced past an email that never went out — but it also left `queued`/`expires` untouched, and the daemon's pickup poll selects on `expires <= NOW()`, so the row was re-selected on the very next pass (~15 s) and every pass after that, indefinitely. A rate-limited recipient (thresholds are per address, instance-wide: 1/min, 10/day, 60/week — an ESM design or a shared lab address reaches them legitimately), an SMTP outage or a missing recipient therefore produced a hot loop that re-knitted the body through OpenCPU and re-fired `notify_study_admin` on every tick, burning metered compute and mailing the owner until someone noticed. A genuine send failure now re-arms `queued`/`expires` at `unit_session.queue_expiration_extension` (default +10 minutes), turning the ~15 s hot loop into ~144 attempts/day (~40× fewer) and collapsing the error mail to roughly one per retry via the notification throttle. Retrying rather than giving up is deliberate: a rate-limit window drains and an outage ends, whereas moving on would silently drop a study's email. Two scope notes from the code review: the "user disabled receiving emails" branch is **not** re-armed — it is a terminal skip that advances on its next pass regardless, so re-arming would only have added a ~10-minute stall with no resend; and the re-arm is a **flat** tier, not the escalating/capped backoff Pause/Branch rechecks get, so a permanently-broken email still retries ~144×/day rather than degrading further. Sharing the escalating mechanism needs the same schema work as the reverted backoff item below; the flat tier is the safe interim (strictly better than the loop it replaces).
- **Importing a run bundle no longer silently unlinks every survey from its Google Sheet — and re-linking it no longer opens an admin-origin XSS.** `SurveyStudy::getSettings()` exports `google_file_id`, but the mass-assignment allowlist added to `createFromData` in `987cfba8` deliberately left it out, so a round-trip through export → import dropped the link with no notice and the run editor's resync button then had nothing to resync. It is now on the allowlist. The first cut of that change (allowlisting alone) opened a **stored-XSS** hole that the code review caught before release: `templates/admin/home.php` and `templates/admin/survey/list.php` echo the id into an `href` via `google_get_sheet_link()` (raw string interpolation) with no `h()`, so a shared run-bundle whose `settings.google_file_id` was a `"><script>` payload executed in the *importing* researcher's admin origin — the exact boundary the study-subdomain split exists to protect. The `google_is_valid_sheet_id()` choke-point guard only covered the filesystem sink (`google_download_survey_sheet()` interpolates the id into a destination filename, so `../` was a write-outside-the-upload-dir primitive). The shipped fix closes both sinks: the id is validated at the **write boundary** in `createFromData` (a bundle with a malformed id imports without the link, not with a payload), and the two unescaped `href`s are now `h()`-escaped (which also neutralises the lower-severity self-inflicted path through the admin settings form). (Host-level SSRF was never reachable — the id lands in the path segment of a fixed `docs.google.com` URL.)

### Reverted before release
- **A rework of the Pause/Branch recheck backoff was attempted and pulled.** Audit F19's escalating backoff (10 min → 1 h → 6 h) is keyed on the unit session's *age*, which conflates "parked for a long time" with "broken for a long time": a longitudinal Pause waiting days that hits its *first* transient OpenCPU blip is demoted straight to the 6-hour tier. The rework re-keyed it on the current failure-streak length (cleared by the first success) and stored the streak start in the `state_log` JSON to avoid a migration. The code review showed that cannot work: `logResult()` rewrites `state_log` on **every** failing pass — it runs via `logOutput()` at the top of `isExpired()`, before the backoff reads it — so the streak resets each pass and the tier never escalates; the shipped unit test passed only because it injected the marker by reflection, bypassing that interplay. A correct version needs the streak start in a field `logResult()` does not own, i.e. a new column, which is out of scope for a patch release. Reverted to the working age-keyed behaviour and tracked for `feature/form_v2` with an integration test that drives a real daemon pass. (The same schema work would let the email retry above share the escalating mechanism.)

## [v1.7.0] - 20.07.2026

(c) `ComputeUsageHelper::formatDuration` applied the integer `%` to its float input, emitting two "float to int loses precision" deprecations per value on every dashboard render and limit email; it now works in whole seconds (`intdiv`), identical output, no deprecation (unit test `tests/ComputeUsageHelperFormatTest.php`).
- **User-detail pagination no longer advertises phantom pages.** The rollup's `n_unit_sessions` counted every unit session of a run, but `RunHelper::getUserDetailTable`'s items query inner-joins `survey_run_units` on `(unit_id, run_id)` — excluding sessions whose unit isn't in the run structure (reminder/special units, removed units) and fanning out a unit placed at multiple positions. So the page count disagreed with the rows shown: an empty trailing page for runs with reminder sessions, or an unreachable partial page for multi-position units. `n_unit_sessions` is now computed with the same `survey_run_units` join in `RunMetrics::reconcileRunMetrics`, so it equals the displayed row count exactly (the live filtered fallback already matched). Regression smoke `bin/test_user_detail_pagination_smoke.php` (red pre-fix: a reminder special-unit session made the rollup count 3 while the table showed 2).
- **File/media result cells prove their value is server-built before rendering it unescaped.** `File_Item` and its Image/Audio/Video subclasses override `getEscapedResult()` to pass their stored embed markup through raw (the `src` is a server `asset_url()` over a `crypto_token()` filename) — but the admin results view dispatches by the item's **current** type, so a column holding data written under a different type (a backup restored via `bin/import-results.php` after a text→file retype) was emitted raw, turning a participant's stored `<img src=x onerror=…>` into script on the admin origin. `getEscapedResult()` now reconstructs an anchored pattern from the item's own `embed_html` (the `%s` slot constrained to an upload-dir URL with no HTML metacharacters) and returns the value raw only on a full-template match — which has no room for an event handler or extra attribute — otherwise `h()`-escaping it. Genuine embeds still render; foreign text/payloads under a file-typed column are escaped. `tests/ItemEscapedResultTest.php` extended (red pre-fix: an XSS payload under a file column passed through raw); the media-passthrough case now builds each class's genuine markup from its own template.
- **The run-engine ops scripts can no longer corrupt what they repair** (three hardenings + one scheduling fix). (a) `sweep_stalled_unit_sessions.php` decided "stale litter" purely by the position-derived current-session lookup — a live row that the run session's `current_unit_session_id` **pointer** still designates (legacy position drift) got terminal-stamped, making the participant's next request advance from the drifted position and skip un-elapsed gates; such rows are now pointer-protected and loudly reported for repair instead. The sweep also gains `--run-id` scoping, and — separately, in the deployment repo — an **ofelia label**: it was scheduled only in `config/formr_crontab`, which docker installs don't use, so it had silently never run there. (b) `heal_duplicate_pause_sessions.php --apply` wrote its plan minutes after computing it, without the run-session lock every other writer holds — a daemon advance in between made the unguarded pointer-repoint rewind `position` onto a completed step (duplicate downstream sends, the exact corruption being healed). Apply now proceeds per run session under `GET_LOCK` (an engine-held lock defers the cluster to a later re-run) and the repoint only fires while the pointer still rests on one of the cluster's superseded rows. (c) `backfill_run_unit_id_active.php` stamped any live NULL row whose unit happened to sit at the run session's current position — for a **multi-position** unit (the exact ambiguity patch 048 left NULL) that manufactures cross-placement adoption; stamping now additionally requires the unit to occupy exactly one position in the run, and each row's write is individually guarded so a 23000 against patch 063's UNIQUE key is reported instead of aborting the run mid-way. Regression smoke `bin/test_ops_scripts_smoke.php` (red pre-fix on (a)-behavior, (b) lock deference, and (c) multi-placement skip).
- **Two "Test Survey" previews no longer destroy each other's in-flight state.** The preview state (study, items, the `unit_session_id` that lets "Next" POSTs resume) lived in a single session slot, so opening survey B's preview in a second tab clobbered survey A's — and tab A's next request past the 15-minute token mark then hit the 410 expired branch (the continue carve-out checks "is A's test live?", which the clobber made false), silently discarding that page's answers; continuing A clobbered B right back. The token already carries the study identity, so the state is now keyed per study (`test_study_data_<id>`), threaded into the TEST_RUN exec via `Run::$test_study_id` — two tabs interleave freely, `Run::testStudy()` semantics otherwise unchanged. Regression smoke `bin/test_survey_test_two_tabs_smoke.php` — real HTTPS against the vhost with one cookie jar (the session cookie is `Secure`; plain HTTP never replays it), red pre-fix; fixture studies must contain an answerable item, since a submit-only survey legitimately finishes on first execute.
- **Repeated `end_external` API callbacks are an idempotent success again.** Audit F20 correctly scoped `endLastExternal` to the newest live External (a delayed callback no longer kills an unrelated current External) — but it also made the method honest about no-ops (`false` when nothing is live), and the V1 handler mapped that straight to **400 "Could not end external unit"**. External services retry callbacks and deliver them late as a matter of course; integrations that treat non-2xx as failure started erroring/alerting on what used to be (and should be) a harmless repeat. The V1 handler now answers a no-op with **200 "No active external unit to end — nothing to do"** — retry-safe like the pre-F20 contract, but with a truthful body (the old code claimed "ended successfully" even when nothing happened). The model's honest `false` is unchanged; legacy V0 always answered 200 and is unaffected. Regression smoke `bin/test_end_external_idempotent_smoke.php` (red pre-fix: repeat call → 400; also pins F20's newest-only ending).
- **Router slugs can no longer be claimed as run names.** In path-based (non-subdomain) deployments the router matches the first URL segment against the route table before falling through to "treat it as a run name" — so a run named after a route slug is silently unreachable, and this branch's new `/survey-test/` route added a fresh collision: a run literally named `survey-test` (legal per the name regex, absent from `reserved_run_names`) would serve every participant a 403 "invalid preview link" while its access code was decrypted as a Halite token. The shipped `reserved_run_names` default now covers every top-level slug (`admin`, `run`, `public`, `survey-test`, plus the internal `formr-test-run`) alongside the existing `api`/`test`/`delegate`, closing the hazard class rather than the one instance. Unit-tested against the dist default (`RunIsReservedNameTest`, red pre-fix). Note: instances that override `reserved_run_names` in their live `settings.php` should extend their copy; a pre-existing run already holding a colliding name must be renamed.
- **Removed the compute dashboard's self-defeating "freshen if stale" scan.** `RunMetrics::reconcileIfStale` probed freshness via `MAX(updated_at)` — but a value-unchanged `INSERT … ON DUPLICATE KEY UPDATE` is a no-op that never advances `ON UPDATE CURRENT_TIMESTAMP`, so on a quiet instance the rollup never read as fresh and **every** superadmin dashboard view re-ran the full 4-way history scan (run sessions, unit sessions, push logs, email logs) — the per-view cost the rollup exists to eliminate, paid exactly when idle. Since the write-time month bucket landed, the dashboard's this-month figures are fresh by construction and the freshen-on-view call has no remaining purpose: it and its single call site are deleted. Lifetime totals refresh with the nightly reconcile (the stated bounded-staleness contract, now noted in the dashboard help text).

Regression smoke `bin/test_structure_replace_smoke.php` (red pre-fix on both paths: a NULL-keyed live session survived while its stamped sibling was expired; uses an Email unit — Pause/Page/etc. override `removeFromRun` to delete the whole unit definition, whose FK cascade is already terminal).
- **Shuffle re-randomizes on every revisit again (audit F18 reverted by design).** F18 made a participant's first-ever group draw sticky per Shuffle unit for the whole run session — but per-revisit re-randomization is the unit's intended contract (a design wanting a constant experimental group keeps the Shuffle outside the loop), and the sticky lookup also silently changed running studies' randomization (loop designs got day 1's draw forever; a unit reused at two positions shared one group). The reuse lookup is removed; what stays from that commit is the F17 crash fix — re-executing the *same* unit session (crash between INSERT and end) is idempotent on the shuffle PK and now reports the originally stored group rather than the losing re-draw. - **Study-admin error emails are no longer silenced for cron-driven testing sessions.** The issue-#608 guard in `Notification::canBeSent` suppressed error notifications for *every* testing-flagged session — including daemon/cron-driven ones, where email is the only error channel (on-screen alerts need a browser). A researcher piloting their run as a testing session before launch — the phase errors are most likely and most fixable — heard nothing when their broken `relative_to` failed in the daemon overnight, and several of this branch's own warnings (e.g. the Branch dangling-jump-target notification) were muted with it. The suppression now applies only in interactive web context (`isTesting() && !formr_in_console()`), where the tester already sees the on-screen alert; console/cron errors email as before, still bounded by the per-run notification throttle. Regression smoke `bin/test_notify_testing_smoke.php` (red pre-fix: testing + console → suppressed).
- **Run-session loop protection simplified to one configurable ceiling that halts instead of ejecting.** The v1.5.0 two-tier design (per-position revisit counter → `spam()` session-end, plus a 200-execution cascade ceiling) had a blind spot its own arithmetic guaranteed: for a skip cycle spanning more than ~40 positions no position could reach 6 visits before the 200-execution halt, so the loop verdict was unreachable and the daemon re-executed ~200 units (incl. R conditions) per poll, forever; the `spam()` path itself also fataled on a null current session. Per the maintainer's call: back to the simple rule — more than `run_session.max_execution_count` automated units in one request (config, default 10) **halts the request without ending the run session**. A misconfigured cycle is now cheap and bounded per request and visible in the error log; a genuine catch-up cascade continues from its advanced position on the next request; no participant is ever spam-ejected (the `spam()` path and per-position tracking are removed). Regression smoke `bin/test_loop_halt_smoke.php` (red pre-fix: a 2-unit skip cycle spam-ended the run session, then fataled). Also aligned `bin/test_run_engine_audit_smoke.php` with the reorder contract from the earlier fix (positions 0/negative valid, duplicates rejected).
- **"Send reminder" fails soft instead of crashing the request.** `Run::sendReminder()` dereferenced the session from `getReminderSession()` unchecked — but a stale/deleted reminder id makes `RunUnitFactory::make` throw outright, and a DB error or non-adoptable UNIQUE collision makes `createUnitSession` install `null` (the audit hardening's explicit failure signal) — either way the single-reminder button 500ed with no alert and a **bulk** reminder request aborted on the first bad session, silently skipping every remaining participant. `sendReminder()` now catches creation failures and returns `false`, which every caller already handles with the "Something went wrong with the reminder" alert, and bulk loops continue with an accurate count. Regression smoke `bin/test_reminder_smoke.php` (red pre-fix: `RuntimeException` escaped `sendReminder` on a nonexistent reminder id).
- **Monthly compute is now charged to the month the work happened, not the month the session was created.** Usage was `SUM(execution_time)` over unit sessions `created` since the 1st — but `execution_time` is a lifetime-cumulative per-session value, so a long-lived session (a Pause waiting weeks, a broken relative_to recheck loop re-executing for months — exactly the recurring burn issue #608 targets) attributed its entire cost to its creation month and escaped every later month's budget; dashboards under-reported the same way. The rollup's `month_execution_time`/`month_key` pair is now **write-time-owned**: `RunMetrics::addMonthExecution()` (called from `UnitSession::addExecutionTime` on every measured pass) accumulates within the month and resets at rollover, the nightly reconcile preserves the bucket instead of clobbering it with the created-date approximation, and both enforcement (`candidateUsers`, now O(runs) instead of an hourly this-month table scan) and the dashboards (`totalsForUser`) read it. Sub-millisecond passes no longer write at all (previously a `+0.000` UPDATE per daemon tick on the hottest table). Trade-off accepted: the month figure is not recomputable from history — a lost hook write under-counts until the bucket self-clears at rollover. Smoke `bin/test_compute_limit_smoke.php` extended (red pre-fix: 999s of this-month compute on a 40-day-old session was invisible to the cron and the run stayed running).
- **Admin email/push/user-detail tables no longer blank out for a day after the rollup migrations.** Patch 068 seeds a `survey_run_metrics` row for every existing run; patch 069 then adds the `n_unit_sessions`/`n_push_logs`/`n_email_logs` columns `DEFAULT 0` with no backfill — so on any upgrading instance every run *has* a rollup row that reads 0, `RunMetrics::count()` only fell back to a live `COUNT` when the row was *missing*, and the three paginated admin views built their pagination from a fake zero (an empty email log that looks like data loss) until the first nightly reconcile — permanently on instances with `metrics_reconcile_enabled = false`. `count()` now treats 0 like a missing row and returns null, so the callers' live-`COUNT` fallback fires: cheap when the run is genuinely empty, correct-at-pre-rollup-cost when the zero is stale, and self-correcting once the nightly pass fills real values. Regression smoke `bin/test_run_metrics_count_smoke.php` (red pre-fix: a zeroed counter paginated the push log at 0 instead of the live 7095).
- **Inline email sends can no longer be double-delivered by the mail daemon.** The F21 idempotency claim in `Email::sendNow` inserted its audit row at `status = 0` with a real `account_id` — exactly the shape `EmailQueue`'s pickup poll (`status = 0 AND account.status = 1`) selects — so on a host with `email.use_queue = false` while `formr_mail_daemon` runs (the docker stack starts it unconditionally), the daemon could grab the claim during the inline SMTP window and send the same email a second time; conversely, a crash between the claim INSERT and `Send()` made the retry treat the orphaned claim as already-sent, silently dropping the email on daemon-less hosts. The claim now goes through `EmailQueue::claimSyncSend()` at a new `STATUS_SENDING (2)` — invisible to the daemon poll — and a duplicate claim is resolved by the row's state: `SENT`/`QUEUED` → handled elsewhere (never send inline); an orphaned in-flight claim or prior failure → adopt and deliver (favouring delivery over a drop). Success now also stamps `sent = NOW()` like the daemon's path, and the admin email log renders the transient status. Regression smoke `bin/test_email_claim_smoke.php` (red pre-fix: the claim surfaced in both daemon poll queries; includes a live-poll control row).
- **Fresh-install baseline `sql/schema.sql` reconciled with the migration line.** A fresh install seeds from `schema.sql` and then marks every patch as applied *without running it* (`build.sh: atlas migrate set <highest>`), so anything a patch adds that was never folded into `schema.sql` is permanently absent on new installs — silently, because the ledger claims the patch ran. The baseline had drifted badly: 14 core tables were missing entirely (`survey_run_metrics`, `survey_study_metrics`, `push_logs`, `push_messages`, `survey_notifications`, `survey_run_secrets`, `oauth_client_runs`, …) and ~27 more had stale definitions (notably `survey_unit_sessions` lacked the whole Track A column set — `run_unit_id`, `iteration`, `state`, `state_log`, `idempotency_key` — from patch 047, and both new UNIQUE keys from 063/064). A fresh install was therefore broken well beyond this branch. `schema.sql` is regenerated from a fully-migrated database for the 45 canonical core tables (a table is canonical iff it is referenced by committed `.php`/`.sql` or created by a committed patch; runtime `s<N>_…` result tables and non-release artifacts are excluded). New guard `bin/check_schema_parity.sh` loads `schema.sql` into a throwaway DB and diffs every core table against a migrated reference, failing on any drift or missing table — run it at release time so this can't silently recur.
- **Re-ordering run units works again under the new UNIQUE (run_id, position) key, and no longer rejects position 0.** Two regressions arrived together: patch 064 promoted `position_run` to UNIQUE (audit F10), but `Run::reorder()` still wrote one `UPDATE` per unit — and MariaDB/InnoDB enforces UNIQUE per row *within* a statement (no deferred constraints), so any permutation that transiently reuses a live position (a plain swap, any rotation, a reorder of a consecutively-numbered run) failed with `23000 Duplicate entry` and rolled back to "Re-ordering failed"; and the F12 validation rejected any position `< 1`, so a run holding a unit at position 0 (a valid slot the rest of the engine now supports) could not be reordered at all because the editor posts every unit's position. `reorder()` now applies the batch in two phases inside one transaction — park every affected row in a band strictly above every current and requested position (collides with neither the not-yet-moved rows nor the finals), then write the finals — as two batched CASE `UPDATE`s (fewer round trips than the old per-row loop). Validation now rejects only *duplicate* positions within a batch; 0 and negative positions are allowed. Regression smoke `bin/test_reorder_smoke.php` (red on the pre-fix method: swap → 23000, position-0 batch → rejected).
- **Destructive survey operations now count the results table itself, never the metrics rollup.** `getResultCount()`'s switch to the write-time `survey_study_metrics` rollup (v1.7.0, SQ-11) had leaked into the gates that guard data deletion: `hasData()`/`hasRealData()`/`deleteResults()`/`backupResults()` decide whether a spreadsheet re-upload may recreate the results table and whether a backup is required first — and an unseeded (fresh patch 069), partial (first hook before the first reconcile) or drifted (direct imports, testing toggles) rollup row reading zero could let a re-upload `DROP`/`TRUNCATE` a populated results table with **no backup**. Those four gates now read a new `getResultCountLive()` (ground truth from the results table, cache-bypassing); the rollup continues to back the frequently-viewed display counts, where bounded staleness is fine. `deleteResults()` additionally resets the study's rollup row so display counts don't keep reporting deleted rows. Regression check: smoke section D (`bin/test_write_time_metrics_smoke.php`) poisons a rollup row to zeros and asserts display serves the rollup while the gates see the live data.
- **A named choice list in a separate `type_options` column is no longer ignored** (user-reported: uploading a sheet with a named choice list in the new format fails with "You forgot to define choices for this item"; also shipped as the v1.4.1 hotfix). The choice-list name was only ever recognised when written inline in the `type` cell (`mc_button mylist`): the parser split that cell at the first space and promoted the list name into `choice_list`, but a `type_options` *column* was stored verbatim and never consulted, so the item reached validation with no list. `Item::__construct` has a fallback that derives `choice_list` from `type_options`, but it never fired for a bare list name (it required more than one token) and ran too late anyway — `ItemFactory::make` attaches the choices *before* constructing the item. When that fallback did fire (multi-token options) it was worse than the error: the item validated with `choice_list` set but an empty `choices` array, and rendered silently without choices. `SpreadsheetReader` now folds a `type_options` column back into the type string before splitting, so both spellings run through one parser. Governing principle, now enforced by `tests/SpreadsheetReaderTypeOptionsTest.php` across 17 type strings: **a `type_options` column means exactly what everything after the first space of the `type` cell means**, for every type. Also makes the merge independent of column order (a `type_options` column left of `type` used to win over the derived value), while an explicit `choice_list` column still takes precedence and the "named choice list *and* a choice1 column" conflict is still raised for both spellings. Regression test is red on the pre-fix reader; verified end-to-end through the real `createFromFile`/`uploadItems` path against a live database.
- **"Test Survey" no longer refuses the submit when the preview outlives its 15-minute token** (user-reported as "submission doesn't work for tested surveys"). The preview token minted by the admin "Test Survey" button expires after 15 minutes to bound how long a leaked link can start new previews — but the expiry check rejected *every* request, including the "Next"/"Finish" POST of a test already underway, so filling a survey for longer than 15 minutes ended in a 410 "Link expired" that silently discarded that page's answers (the pre-1.3.0 admin-session preview never expired mid-test). An expired-but-authentic token now *continues* a test that is already in flight in the same browser session (the `/survey-test/` session's `test_study_data` proves it started while the token was valid) and is still refused otherwise; finishing the test re-arms the refusal, so the replay window for leaked links is unchanged. Regression spec `tests/e2e/survey-test-token-expiry.spec.js` (red on the pre-fix controller); verified live end-to-end — answers POSTed after expiry are saved and the test finishes, while the same expired token in a fresh browser still gets 410.

Each unit session now records the cumulative wall-clock seconds it spent executing, including OpenCPU/R calls, in a new `survey_unit_sessions.execution_time` column. `UnitSession::execute()` is wrapped in a monotonic `hrtime()` timer whose `finally` clause accumulates onto the column via an in-place `COALESCE(...) + delta` increment (so units that execute repeatedly — surveys paging forward, pauses re-checked by the daemon — add up, per the issue's open question, and concurrent passes never lose time to a read-modify-write race). Timing is best-effort: a failed/missing-column write is logged and swallowed, never breaking a participant's run. Two read-only dashboards surface it: **`/admin/compute`** for study admins (their own runs — total, this-month, and per-run totals with avg/slowest/last-activity), and **`/admin/advanced/compute_usage`** for superadmins (instance-wide, broken down by user and by heaviest run). Both exclude pre-feature rows (`execution_time IS NULL`) so totals reflect only measured compute. New `application/Helper/ComputeUsageHelper.php` holds the aggregate queries and a duration formatter. Regression-tested in `tests/e2e/compute-dashboard.spec.js`. **Coverage note:** the `execute()` wrap captures all participant run-traversal compute — survey render + paging + submission, Branch/Pause `relative_to`, External R, and Email/Push rendering (web and daemon). It does **not** count admin-side OpenCPU (survey-test preview, the `advanced/test_opencpu*` tools), which is dev activity rather than study resource use.
- **Configurable monthly compute limits, auto-closing over-budget studies** (issue #608). A per-user monthly compute budget (seconds of execution time summed across all the owner's runs in the current calendar month). The effective limit is the per-user `survey_users.compute_limit_monthly` when set, else the instance-wide `compute_limit_monthly_default` config; in both, **0 = unlimited and is the default**, so nothing is limited out of the box. A new hourly cron (`bin/cron_compute_limits.php` → `application/ComputeLimitCron.php`) enforces it: when a user is over budget it sets every still-public run of theirs to `public = 0`, remembering the prior level in a new `survey_runs.compute_closed_from` column, and emails them once (`email/compute-limit-reached.ftpl`); when usage drops back under the limit (typically when the month rolls over) it restores those runs to their prior visibility and emails once (`email/compute-limit-restored.ftpl`). Runs the owner closed by hand are never touched. Limits are **superadmin-set only** — run owners cannot change their own — via an editor on the superadmin compute dashboard (plain PRG form, no inline JS, CSP-safe). When the global default is 0 (the open-source default), the cron only considers users with an explicit override, so it stays cheap.

The error now appears as a red banner + collapsible `<details>` block with the full debugger output, in the spot the iframe would have rendered.
- **`notify_user_error` surfaces the error body in admin contexts too.** Gate broadened from `$run_session && (isCron || isTesting)` to `!$run_session || isCron || isTesting`. Real participants still see only the public_message; admin-context callers (no `$run_session`) and cron / queue daemons see the actual error. Matches the same logic that drives `$show_errors='TRUE'` in the OpenCPU helpers.
- **`SurveyResource::updateSurvey` tmp file cleanup.** Google-Sheet download is now wrapped in try/finally so the tmp file is removed on the `uploadItems` exception path too. Matches the pattern already used by `createOrUpdateSurvey`.
- **`OAuthHelper::createClientInternal` wraps the credential creation in a real transaction.** `Site::getOauthServer()` now passes the shared `Site::getDb()->pdo()` into `HashedTokenOAuth2StoragePdo`, so the stub `INSERT`, the `setClientDetails` `UPDATE`, and the `replaceClientRuns` writes commit or rollback as a unit. Previously the storage layer had its own PDO connection and a `setClientDetails` failure could leave a stub credential with empty scope/secret.

### Security
- **Strict identifier validation in `DB_Select::order()`.** The previous pass-through let any string flow into `ORDER BY` verbatim. A future caller threading a `?sort=` request param to `paginate['order_by']` would have been a SQLi sink (UNION-based row exfiltration). The new `parseStrictIdentifier()` accepts only `column` or `table.column` (with optional backticks); SQL function calls (`RAND()`, `COUNT(*)`, `COALESCE(...)`) now require the new `DB::raw()` escape hatch.
- **Parameterised the last interpolating SQL helpers.** `DB::like()` was discarding `PDO::quote()`'s return value and concatenating user input into a LIKE literal, which let any `name=` filter forwarded to the v1 API break out of the `WHERE user_id = ?` clause. Two `LIKE`/`session = '...'` sites in `UserHelper::getUserManagementTablePdoStatement` (superadmin `email` filter) and `SurveyStudy` (admin results `session` filter) had the same shape and are now bound through `:placeholder` with wildcard escaping.
- Operators are encouraged to upgrade and to rotate any OAuth client secrets after upgrading. A detailed advisory will follow once adoption is broader.

## [v0.25.7] - 09.05.2026
### Fixes
- **Prevent duplicate cascade ("double expiry").** Observed in prod on AMOR 2026-05-09 at 10:03–10:11: 18 participants received 2× ESM email + 2× push notifications and ended up with two Survey unit-session rows from one Pause(124) anchor (one participant got four cascades within five seconds). ## [v0.25.6] - 08.05.2026
### Fixes
- **Survey expiry algorithm rewrite** to match the [Expiry wiki spec](https://github.com/rubenarslan/formr.org/wiki/Expiry). The pre-fix code walked three rules (inactivity, start-window, grace) in fixed order with each *overwriting* the previous; the rewrite combines them per the wiki's pre/post-access formula (pre-access: `invitation+X`; post-access: `MIN(invitation+X+Y, last_active+Z)`). Eliminates the originally-reported bug where surveys with `X=60, Y=0, Z=0` expired participants who were actively editing. `application/Model/RunUnit/Survey.php`.
- **Cron stale-reference branch no longer advances the run.** When the queue daemon picks up a unit-session whose run-session has already moved past it, `RunSession::execute()` previously called `removeItem()` AND `moveOn()` — the moveOn cascaded `createUnitSession` calls past the participant's still-active unit, and the supersede side-effect orphaned that active unit's queue entry. Symptom A in the wild: `ended IS NULL, expired IS NULL, queued = -9` while the participant was mid-survey. Now drops the stale reference and stops; active unit-session preserved. `application/Model/RunSession.php:247-251`.
- **Supersede side-effect scoped to same `unit_id`.** `UnitSession::create()` flipped *every* queued sibling in the run-session to `queued=-9`, regardless of unit. The blanket scope amplified the cron-stale-reference orphan path and could clobber unrelated queued ESM Surveys during a moveOn cascade. Now scopes the supersede WHERE clause to `unit_id = $this->runUnit->id`, catching only genuine duplicates from back-jumps. `application/Model/UnitSession.php:66-70`.
- **`getCurrentUnitSession` excludes superseded siblings.** The query filtered on `ended IS NULL AND expired IS NULL` but not on `queued`, so once an active sibling's `ended` got set, ORDER BY id DESC LIMIT 1 returned the older `queued=-9` ghost.   * Reminders are sent 6, 2, and 1 month(s) and 1 week and 1 day before expiry.
  * To avoid spamming, we only send a reminder if the run has not received a reminder in the last 6 days.
  * If the study owner has received 2 reminders and the first reminder was at least two weeks ago, we delete the run data.
  * The expiry routine is configured in such a way that run data may not be deleted on the day of expiry if the study owner was not given sufficient notice (e.g., because of problems with the email server or because they recently changed their expiry date).
* Orphaned files which were uploaded within a survey are now automatically deleted every night.

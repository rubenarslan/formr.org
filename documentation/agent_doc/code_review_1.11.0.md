### 1a — correctness (PHP)

- `/home/admin/formr-docker/formr_source/application/Model/RunUnit/Email.php:632-633` (`embeddedImageCid`) — `rawurlencode()` does not match R's `URLencode(basename(x))` (default `reserved=FALSE`) used in `/home/admin/formr-docker/formr_source/application/Functions.php:1996`'s `opts_knit$set(upload.fun=...)`. R's default `URLencode` leaves `$ _ . + ! * ' ( ) , ; / ? : @ = &` unescaped (only its "reserved" character class plus alnum/`-._~` is safe there), while PHP's `rawurlencode` (RFC 3986 unreserved-only: `A-Za-z0-9-._~`) percent-encodes all of those. — Failure scenario: an R Markdown chunk label containing e.g. parentheses, `+`, `&`, `!`, or a comma (`{r "my plot (v2)"}` → figure `my plot (v2)-1.png`) produces an HTML `cid:my plot (v2)-1.png` (R leaves those chars raw) that no longer matches the PHP-registered Content-ID `my%20plot%20%28v2%29-1.png` (PHP escapes them) — same "image never renders" bug class as #290, just for a different character set, and the new `EmailEmbeddedImageCidTest` only exercises spaces so it doesn't catch this.

- `/home/admin/formr-docker/formr_source/application/Spreadsheet/SpreadsheetReader.php:485-501` (`findMergedCells`, Xlsx/ZipArchive branch) — labels merged ranges as `'worksheet ' . $m[1]`, where `$m[1]` is the numeric suffix of the underlying `xl/worksheets/sheetN.xml` part name. That number is assigned at file-creation time and is **not** kept in sync with the visible tab order or name after sheets are reordered, renamed, or deleted/recreated in Excel (the real order/names live in `xl/workbook.xml` + `xl/_rels/workbook.xml.rels`). — Failure scenario: a user reorders or renames sheets (e.g. their visible 1st tab "survey" is physically `sheet3.xml`); the refusal message says "merged cells (worksheet 3!C2:D2)", which doesn't correspond to anything the user sees, making the range impossible to locate. This is also inconsistent with the Ods/xls fallback branch just below (`SpreadsheetReader.php:502-506`), which correctly uses `$ws->getTitle()`.

- `/home/admin/formr-docker/formr_source/application/Spreadsheet/SpreadsheetReader.php:485` and `:502-506` (`findMergedCells`) — scans **every** worksheet in the workbook (all `sheetN.xml` parts for xlsx; `$spreadsheet->getAllSheets()` for the fallback), not just the `survey`/`choices` sheets that `readItemTableFile` actually parses. — Failure scenario: a spreadsheet with a decorative/notes/instructions tab that happens to contain merged cells (common — title banners, credit lines) gets its entire upload refused with "formr cannot read merged cells," even though those merged cells are on a sheet formr never reads and can't corrupt anything. This is a false-positive regression for uploads that worked fine before #111's fix.

### 1c — reuse / simplification / efficiency / altitude

- `/home/admin/formr-docker/formr_source/tests/SpreadsheetReaderDuplicateNameTest.php:22-45` and `/home/admin/formr-docker/formr_source/tests/SpreadsheetReaderMergedCellsTest.php:22-46` — [reuse] both add yet another private `makeWorkbook()` that writes an in-memory `PhpOffice\PhpSpreadsheet\Spreadsheet` to a `tempnam()` `.xlsx`/`.ods` and cleans up via a `$tmpFiles` array in `tearDown()`. This is a near-verbatim copy of `tests/SpreadsheetReaderRowCapTest.php:41-65`'s `makeWorkbook(array $sheets, $strayOnSheet = null)` (same loop shape, same `tmpFiles`/tearDown pattern), which itself sits alongside two more independent xlsx-fixture builders in `tests/SpreadsheetReaderBlankChoiceListTest.php:25-43` and `tests/SpreadsheetReaderTypeOptionsTest.php:28-50`. This diff brings the count of hand-rolled "build an xlsx fixture via PhpSpreadsheet, tempnam it, delete in tearDown" implementations in `tests/` to five, each with a slightly different signature (`array $sheets`, `array $sheets, $strayOnSheet`, `$format, $mergeRange`, `array $header, array $row`). Cost: any future change to how fixtures are built (e.g. switching temp dir, writer engine, or adding a `.xls` fixture for the merge test noted as untested) has to be applied in up to five places; a shared `tests/SpreadsheetFixtureTrait.php::makeWorkbookFile($sheets, $format = 'Xlsx', $mergeRange = null)` would have covered all five call sites including these two new ones in one place.

- `/home/admin/formr-docker/formr_source/bin/test_run_unit_delete_push_smoke.php:19-25` (`ok()`/`alertsText()`) — [reuse] re-implements the same `function ok($cond, string $label): void { global $failures; ... }` boilerplate that already exists, byte-for-byte in shape, in essentially every one of the ~20 other `bin/*_smoke.php` scripts (`test_batch_update_smoke.php:19`, `test_compute_limit_smoke.php:30`, `test_email_claim_smoke.php:28`, `test_loop_halt_smoke.php:30`, `test_reorder_smoke.php:25`, `test_run_engine_audit_smoke.php:26`, etc.) — there is no shared `bin/smoke_bootstrap.php`. This diff was the natural point to introduce one: it adds both the new smoke script *and* `documentation/agent_doc/releasing.md`, which for the first time formalizes running "`for f in bin/*_smoke.php; do … php "$f" …; done`" as a mandatory pre-release gate — i.e. the moment these scripts stopped being one-off diagnostics and became a battery worth treating as a suite. Cost: ~20+ duplicate `ok()`/counter implementations that will keep growing every time a new regression gets a smoke; a one-time extraction (`ok()`, a `$failures` counter object, and the common `require_once .../setup.php`) would shrink every future smoke by ~10 lines and give the new "gate" in `releasing.md` one place to add shared reporting (e.g. a summary table) instead of parsing 20 scripts' stdout.

- `/home/admin/formr-docker/formr_source/application/Spreadsheet/SpreadsheetReader.php:483-511` (`findMergedCells`) — [efficiency] runs on *every* item-table upload, unconditionally reopening the just-parsed `.xlsx` a second time as a `ZipArchive` and regex-scanning the full worksheet XML of every sheet (`preg_match_all` over `getFromIndex($i)` for each `xl/worksheets/sheetN.xml`), in addition to the `PhpSpreadsheetReader->load()` pass that already ran seconds earlier in `readItemTableFile()`. For the overwhelmingly common case (no merged cells, which is why `setReadDataOnly(true)` was chosen for affordability in the first place per the docblock at `:475-479`) this is pure waste: a second full unzip-and-decompress of every worksheet part on every survey/choices upload just to conclude "nothing found." Cheaper alternative that avoids the second read entirely: derive `$merged` from the same `ZipArchive` handle PhpSpreadsheet's own Xlsx reader already opened internally (not exposed, so would need a small upstream shim), or — simpler — only do the zip/XML scan lazily, after a first cheap heuristic (e.g. reading just `xl/worksheets/sheet1.xml`'s size/first bytes for a `<mergeCell` substring via `fgets` on a stream) fails to rule it out; as written, every upload pays a full second decompression pass for a check that almost always finds nothing.

- `/home/admin/formr-docker/formr_source/application/Spreadsheet/SpreadsheetReader.php:568-586` (catch block dual-path) — [altitude] the `if ($this->errors) { … } else { … }` branch exists only to guess, from a side-channel array's state, whether the caught `\Throwable` originated from formr's own cell-validation code (`readSurveySheet()`/`readChoicesSheet()`, which push a row message at e.g. `:714`/`:864` and then `throw` a wrapped copy at `:727`/`:941` *without clearing `$this->errors`*) or from something genuinely foreign (a corrupt file, a PhpSpreadsheet internal `TypeError`). The actual duplication bug (#385) is created at the throw sites, not discovered at the catch site — each throw leaves the stale unwrapped message(s) sitting in `$this->errors` for the catch block to stumble over and infer intent from. That inference is correct today only because of an implicit invariant (every `$this->errors[]` push in the row loop is immediately followed, same iteration, by the `if ($this->errors) { … throw … }` check at `:727`/`:941`) that isn't structurally enforced — a future contributor who adds a validation error somewhere in the loop without pairing it with an immediate throw would silently break the catch block's heuristic (a real error would get swallowed into the "generic" branch, or a later foreign exception would get misreported as one of ours). The deeper fix belongs at the throw site: either clear `$this->errors` right before throwing (`$this->errors = array(); throw new …($error);`) so the array is a reliable "was this ours" signal, or better, throw a dedicated `SpreadsheetValidationException` there so the catch block dispatches on exception type (`catch (SpreadsheetValidationException $e) { $this->errors = [$e->getMessage()]; } catch (\Throwable $e) { … generic … }`) instead of on array contents — removing the need to reason about `$this->errors`'s state across two unrelated methods at all.

- `/home/admin/formr-docker/formr_source/application/Spreadsheet/SpreadsheetReader.php:483-511` (`findMergedCells`, whole approach) — [altitude] the fix treats "merged cells" as something to detect-and-refuse, which is why it needs the zip/XML detour at all (`setReadDataOnly(true)` drops merge info, so refusing requires a second, structure-aware read). But the actual complaint in #111 is narrower: "merged cells read as blanks, so a merged header or label produced errors further down that pointed at the wrong place" — i.e. the covered (non-anchor) cells of a merge lose the value that Excel/LibreOffice visually shows for them. PhpSpreadsheet's own non-data-only reader already models a merge as "content lives on the anchor cell, other cells in the range are hidden but the *value* is still attributable to the anchor" (`Worksheet::MERGE_CELL_CONTENT_HIDE`, `Reader/Xlsx.php:1012-1018`). A fix at that depth — read merges *with* `setReadDataOnly(false)` (or a second, deliberately cheap non-data-only pass restricted to the `survey`/`choices` sheets only) and backfill each covered cell with its anchor's value before the row loop runs — would make merged header/label rows parse correctly instead of erroring, matching how a human opening the file in Excel reads it, and would need no `ZipArchive`/regex layer, no "worksheet N vs sheet name" mismatch, and no "unmerge and re-upload" round trip for the uploader. Refusing outright is a defensible, much smaller patch, but it's solving "merges read as blanks" one level higher than where the blankness is actually introduced.

# Slow / Inefficient MariaDB Query Audit — 2026-07

Scope: `formr_source` application PHP (excludes deployment repo). All
findings below were generated by 10 parallel code-reading shards and
then adversarially checked with live `EXPLAIN` against the dev
instance's MariaDB (`formr_db`, `formr.researchmixtape.com`'s
backing DB — real production-shaped data, not synthetic fixtures).
**No code changes were applied by this audit — every remediation is
a suggestion for a human to review and apply separately.**

## 1. Executive summary

393 queries were read across 10 shards; 73 were flagged as
potentially slow. Adversarial `EXPLAIN` verification against the
live dev DB (116k–120k-row `survey_unit_sessions`, 114k-row
`survey_items_display`, 93k-row `survey_run_sessions`) **refuted 19
of the 73** (26%) — mostly cases where a finder assumed a missing
index but the optimizer actually had a usable one, or assumed
`RAND()`/`IN()`/`LIKE` scan cost that the live data didn't
reproduce at current scale. That leaves **54 findings that survive
verification**: 37 confirmed by `EXPLAIN`, 4 real-but-currently-
unverifiable because the backing table is empty/tiny in dev
(`needs-data`), and 13 structural (DML loops, connection overhead,
N+1 patterns) that no single `EXPLAIN` can characterize
(`not-explainable`).

**Top 8 findings, ranked by real impact today:**

1. **SQ-01** `SurveyStudy::getItemDisplayResults` (`SurveyStudy.php:897`) — unbounded export streams the whole study's `survey_items_display` with an unsatisfiable 4-table `ORDER BY`, forcing a filesort every click. High/confirmed.
2. **SQ-02** `RunHelper::getUserOverviewExportPdoStatement` (`RunHelper.php:213`) — full `ALL` scan of `survey_run_sessions` (92,959 rows) on every "Export user overview" click for a large run, no `LIMIT`. High/confirmed.
3. **SQ-03** `ComputeLimitCron::candidateUsers` (`ComputeLimitCron.php:54`) — hourly cron walks essentially the entire `survey_run_sessions`/`survey_unit_sessions` history (~118,888 rows) because the month-start filter lives inside `SUM(CASE...)` instead of the `WHERE`/`JOIN`. High/confirmed.
4. **SQ-04** `RunUnit::endLiveSessionsAtPlacement` (`RunUnit.php:211`) — every unit removal / structure-replace UPDATE scans ~14,792 rows (the whole "still live" tail) because no index leads with `run_unit_id`. High/confirmed.
5. **SQ-05** `UnitSessionResource::handle` (`Api/V1/UnitSessionResource.php:89`) — public/API poll-dashboard endpoint full-scans+filesorts all 116,427 rows of `survey_unit_sessions` for large runs. High/confirmed.
6. **SQ-06** `RunHelper::getUserDetailTable` count query (`RunHelper.php:235`) — full covering-index scan of the entire `survey_unit_sessions` table for the dominant run, **and** a real pagination-count correctness bug (omits the `run_id2` filter the sibling query applies). High/confirmed.
7. **SQ-39** `RunSession::positionSessions` (`RunSession.php:1095`) — admin bulk "send selected users to position" has no cap on the selected-sessions array and issues thousands of sequential queries/locks per request. High/structural (not-explainable).

shards, each read end-to-end by a separate pass:

- `unit-session` — `application/Model/UnitSession.php` (38)
- `survey-study` — `application/Model/SurveyStudy.php` (31)

- `queues-cron` — `application/Queue/*.php`, `application/*Cron.php` (26)
- `run-units` — `application/Model/RunUnit/*.php` (51)
- `helpers-services` — `application/Helper/*.php` (excl. RunHelper/UserHelper covered above where noted), `application/Services/*.php` (45)
- `controllers` — `application/Controller/Admin*.php` (26)
- `api-models-rest` — `application/Api/V1/*.php`, `application/Spreadsheet/*.php`, remaining `Model/*.php` (63)
- `bin-root` — `bin/*.php` (excluding the exclusions below) + top-level `application/*.php` singletons (`DB.php`, `Site.php`) (33)

**393 queries reviewed total; 73 flagged** as candidates. Every
flagged query was then independently re-verified with adversarial
`EXPLAIN` / `EXPLAIN FORMAT=JSON` (and, where the claim was about
round-trip count rather than plan, live `SHOW STATUS LIKE
'Handler%'` deltas) against the running dev DB — not just re-read
from the code.

**Excluded from scope**, per audit instructions:

- `bin/test_*` — live-MariaDB integration smokes (`bin/test_track_a_*_smoke.php`), not production code paths.
- `bin/heal_*`, `bin/*_fixture*` — one-shot remediation/fixture scripts already covered structurally where they touch a shared model method, but not independently audited as "slow" (they're expected to run once, out-of-band).
- `templates/*` — presentation layer; no direct SQL.

**Verification data.** Live dev DB at the time of this audit:
`survey_unit_sessions` 116,426–120,297 rows (count drifted slightly
across the audit as the daemon processed live traffic — evidence
strings cite whichever count was current at test time),
`survey_items_display` 114,576–114,655 rows, `survey_run_sessions`
92,958–94,160 rows, `survey_runs` 88 rows, one dominant run (id=4,
~91,473 sessions — 98% of `survey_run_sessions`) that repeatedly
changed which access path the optimizer chose.

**Limits:**

- `performance_schema` and the slow query log are **OFF** on this
  instance (confirmed in the tools-report scan) — all timing
  evidence below is `EXPLAIN`-plan/rows-examined based (access
  type, key used, filesort/temporary flags, `Handler_read_*`
  deltas), not measured wall-clock query latency. See §6 for a
  proposed dynamic-capture follow-up.
- Several flagged tables are empty or tiny in dev
  (`survey_email_log`, `survey_notifications`, `survey_run_secrets`,
  token tables) — those findings are marked `needs-data`: the
  structural gap (missing index, unindexed predicate) is confirmed
  by schema + `EXPLAIN` shape, but real-world row-scan cost can't be
  demonstrated until the table has production-scale rows.
- Dev-scale row counts and value distributions (e.g. only 3
  `Shuffle`-type units total; only one run at 98% of
  `survey_run_sessions`) mean some "confirmed" findings are
  confirmed *for this run's shape specifically* — a differently
  skewed production instance could pick a different (better or
  worse) access path for the same query.

#### SQ-01 — `SurveyStudy::getItemDisplayResults` unbounded export filesort
**File:** `application/Model/SurveyStudy.php:897` · **Severity:** high · **Verdict:** confirmed

```sql
SELECT survey_run_sessions.session, survey_items_display.session_id AS unit_session_id,
       survey_items_display.item_id, survey_items.name AS item_name, survey_items_display.answer,
       survey_items_display.created, survey_items_display.saved, survey_items_display.shown,
       survey_items_display.shown_relative, survey_items_display.answered,
       survey_items_display.answered_relative, survey_items_display.displaycount,
       survey_items_display.display_order, survey_items_display.hidden
FROM survey_items_display
LEFT JOIN survey_unit_sessions ON survey_unit_sessions.id = survey_items_display.session_id
LEFT JOIN survey_run_sessions ON survey_run_sessions.id = survey_unit_sessions.run_session_id
LEFT JOIN survey_items ON survey_items_display.item_id = survey_items.id
WHERE survey_items.study_id = :study_id
ORDER BY survey_run_sessions.session, survey_run_sessions.created,
         survey_unit_sessions.created, survey_items_display.display_order
```

**Why slow:** `ORDER BY` spans four columns across three joined
tables — no composite index can satisfy that, so MariaDB must
filesort the entire per-study join result. `AdminSurveyController::
exportItemdisplayAction` calls this with `$paginate=null,
$rstmt=true` — streams every `survey_items_display` row for the
study with no `LIMIT`.

**EXPLAIN evidence:** `study_id=20` (largest study): `survey_items`
shows `Using index; Using temporary; Using filesort` (79 rows),
`survey_items_display` joins via `id_idx` (161 rows/item) — **~12,719
rows** filesorted for this one study's export.

**Suggested remediation:** Sort in the application after fetching
(the result set is already bounded by study size, not by the sort),
or add a covering index ordered by the actual output need, e.g.:
```sql
-- sketch only — validate against real access pattern before applying
ALTER TABLE survey_items_display ADD INDEX idx_session_display_order (session_id, display_order);
```
and drive the `ORDER BY` off `survey_unit_sessions.created` via a
pre-sorted session list rather than a 4-table composite sort.

#### SQ-02 — `RunHelper::getUserOverviewExportPdoStatement` full-table scan, no LIMIT
**File:** `application/Helper/RunHelper.php:213` · **Severity:** high · **Verdict:** confirmed

```sql
SELECT survey_run_sessions.position, survey_units.type AS unit_type, survey_run_units.description,
       survey_run_sessions.session, survey_run_sessions.created, survey_run_sessions.current_unit_session_id,
       survey_run_sessions.last_access, us.result, us.result_log, us.expires
FROM survey_run_sessions
LEFT JOIN survey_runs ON survey_run_sessions.run_id = survey_runs.id
LEFT JOIN survey_run_units ON survey_run_sessions.position = survey_run_units.position
       AND survey_run_units.run_id = survey_run_sessions.run_id
LEFT JOIN survey_units ON survey_run_units.unit_id = survey_units.id
LEFT JOIN survey_unit_sessions us ON survey_run_sessions.current_unit_session_id = us.id
WHERE survey_run_sessions.run_id = :run_id
ORDER BY survey_run_sessions.session != :admin_code, survey_run_sessions.last_access DESC
```

**Why slow:** `ORDER BY <expr> != :admin_code, last_access DESC`
sorts on a computed boolean — no index can satisfy it — and unlike
the paginated on-screen table, the **export variant has no LIMIT**,
so the entire run's session list is buffered and sorted on every
"Export user overview" click. Also fires from
`AdminRunController.php:138` (`exportUserOverviewAction`) — same
statement, second call site, deduped here.

**EXPLAIN evidence:** dominant run (id=4, 98% of the table):
`type=ALL, key=NULL` on `survey_run_sessions` despite
`fk_survey_run_sessions_survey_runs1_idx` being a possible key —
optimizer correctly rejects it as unselective for this run, but that
means a **full 92,959-row scan** plus filesort, every export click.

**Suggested remediation:** Compute the "admin code first" ordering
in PHP after fetching (cheap — it's a boolean partition of an
already-fetched result), so the DB-side `ORDER BY` can stay
`last_access DESC` (indexable) or, for the export path specifically,
drop the "admin session first" ordering entirely since exports are
consumed programmatically, not visually scanned top-down.

#### SQ-03 — `ComputeLimitCron::candidateUsers` hourly full-history fan-out
**File:** `application/ComputeLimitCron.php:54` · **Severity:** high · **Verdict:** confirmed

```sql
SELECT u.id, u.email, u.first_name, u.last_name, u.compute_limit_monthly,
       COALESCE(SUM(CASE WHEN us.created >= :month_start THEN us.execution_time END), 0) AS month_used,
       COUNT(DISTINCT CASE WHEN r.public > 0 THEN r.id END) AS open_runs,
       COUNT(DISTINCT CASE WHEN r.compute_closed_from IS NOT NULL THEN r.id END) AS closed_runs
FROM survey_users u
JOIN survey_runs r ON r.user_id = u.id
LEFT JOIN survey_run_sessions rs ON rs.run_id = r.id
LEFT JOIN survey_unit_sessions us ON us.run_session_id = rs.id
WHERE :default_finite = 1 OR u.compute_limit_monthly IS NOT NULL
   OR EXISTS (SELECT 1 FROM survey_runs rc WHERE rc.user_id = u.id AND rc.compute_closed_from IS NOT NULL)
GROUP BY u.id, u.email, u.first_name, u.last_name, u.compute_limit_monthly
```

**Why slow:** runs hourly (`formr_crontab`). `month_start` is only
applied inside `SUM(CASE...)`, not the `JOIN`/`WHERE`, so it doesn't
prune the fan-out at all. `:default_finite=1` (true on any instance
that actually enforces compute limits — the reason this cron exists)
makes the `WHERE` always-true, so effectively this is an unfiltered
4-table join+`GROUP BY` over the **entire historical dataset**,
every hour, forever, growing linearly with total unit-session count
rather than with "this month's" volume.

**EXPLAIN evidence:** `r ALL 88 rows (Using temporary; Using
filesort)`, `rs ref rows≈1351/run`, `us ref idx_uxec_compute
rows=1` → **≈118,888 rows traversed**, essentially all of
`survey_run_sessions` (94,160) / `survey_unit_sessions` (120,297).

**Suggested remediation:** Push the date bound into the `JOIN`:
```sql
LEFT JOIN survey_unit_sessions us
  ON us.run_session_id = rs.id AND us.created >= :month_start
```
and compute `open_runs`/`closed_runs` as a separate un-joined
subquery against `survey_runs` alone (they don't need the
session/unit-session join at all) — or, since this checks a
*monthly* limit, maintain a precomputed monthly rollup table updated
incrementally instead of recomputing from raw history every tick
(see §6).

#### SQ-04 — `RunUnit::endLiveSessionsAtPlacement` scans the whole "still-live" tail
**File:** `application/Model/RunUnit/RunUnit.php:211` · **Severity:** high · **Verdict:** confirmed

```sql
UPDATE survey_unit_sessions
SET expired = NOW(), queued = 0, result = COALESCE(result, 'unit_removed_from_run'), state = :state
WHERE run_unit_id = :run_unit_id AND ended IS NULL AND expired IS NULL
```

**Why slow:** no index on `survey_unit_sessions` leads with
`run_unit_id` (`idx_run_unit_iter` is `(run_session_id, run_unit_id,
iteration)` — leftmost-prefix rules it out for a `run_unit_id`-only
predicate). Called from the base placement-scoped `removeFromRun()`
shared by `Survey`/`Email`/`PushMessage` units, and once per removed
unit during a run-structure replace (`Run.php:1530`,
`replaceUnits()` — same missing-index root cause, see below).

**EXPLAIN evidence:** `run_unit_id=8`: `type=range, key=ended,
rows=14792` — the optimizer substitutes the `ended` index (12% of
the table where `ended IS NULL`) and filters `run_unit_id`
row-by-row after. That's **~6x more rows examined than the ~2,314
actually matching** `run_unit_id=8`, and the scan cost is constant
(~14,792) regardless of which unit is being removed, every time.

**Suggested remediation:**
```sql
-- sketch — leading run_unit_id lets this UPDATE seek directly
ALTER TABLE survey_unit_sessions ADD INDEX idx_run_unit_id_live (run_unit_id, ended, expired);
```
Same index also benefits `Run::replaceUnits` (`Run.php:1530`, SQ-09
below) — same join shape (`ru.id = us.run_unit_id`), same
14,792-row constant scan on every structure-replace API call.

#### SQ-05 — `UnitSessionResource::handle` API poll endpoint full-scans+filesorts
**File:** `application/Api/V1/UnitSessionResource.php:89` · **Severity:** high · **Verdict:** confirmed

```sql
SELECT us.id AS unit_session_id, srs.session, srs.testing, us.unit_id, u.type AS unit_type,
       COALESCE(ru.description, rsu.description) AS unit_description, ru.position, us.iteration,
       us.created, us.expires, us.ended, us.expired, us.result, us.state
FROM survey_unit_sessions us
INNER JOIN survey_run_sessions srs ON srs.id = us.run_session_id
LEFT JOIN survey_units u ON u.id = us.unit_id
LEFT JOIN survey_run_units ru ON ru.unit_id = u.id AND ru.run_id = srs.run_id
LEFT JOIN survey_run_special_units rsu ON rsu.id = u.id AND rsu.run_id = srs.run_id
WHERE srs.run_id = :run_id
ORDER BY us.run_session_id ASC, us.created ASC, us.id ASC
LIMIT 1000 OFFSET 0
```

**Why slow:** doc comment explicitly names this endpoint for
"periodic poll-based dashboards" (a `since`-filter incremental poll
pattern). No index covers `(run_session_id, created, id)` after the
`run_id` join — `idx_uxec_compute` and `idx_run_unit_iter` don't
match. OFFSET-based pagination re-sorts the whole per-run result on
every poll tick.

**EXPLAIN evidence:** `run_id=4` (91,473/92,958 sessions): `us`
`type=ALL key=NULL rows=116427 (Using where; Using filesort)` — full
table scan, no index used at all for the join+order.

**Suggested remediation:** add a covering index and switch to
keyset (seek) pagination instead of `OFFSET`:
```sql
ALTER TABLE survey_unit_sessions ADD INDEX idx_run_session_created_id (run_session_id, created, id);
```
```sql
-- keyset pagination sketch
... WHERE srs.run_id = :run_id AND (us.created, us.id) > (:last_created, :last_id)
ORDER BY us.created ASC, us.id ASC LIMIT 1000
```

#### SQ-06 — `RunHelper::getUserDetailTable` count query: full-table scan + pagination-count bug
**File:** `application/Helper/RunHelper.php:235` · **Severity:** high · **Verdict:** confirmed

```sql
SELECT COUNT(survey_unit_sessions.id) AS count
FROM survey_unit_sessions
LEFT JOIN survey_run_sessions ON survey_run_sessions.id = survey_unit_sessions.run_session_id
LEFT JOIN survey_run_units ON survey_unit_sessions.unit_id = survey_run_units.unit_id
WHERE survey_run_sessions.run_id = :run_id
```

**Why slow:** anchor is `survey_unit_sessions` (116k+ rows), only
filtered indirectly via a 1-hop join to `run_id`; the join to
`survey_run_units` matches on `unit_id` alone (no `run_id`), so a
unit reused across runs multiplies matched rows.

**EXPLAIN evidence:** dominant run (id=4, 98% of sessions):
`type=index, key=session_uq, rows=116427` — a full covering-index
scan of the **entire table**, because at 98% selectivity the
optimizer correctly abandons the `run_id` index. Real execution
returned `count=91473` in ~0.35s query time.

**Correctness bug found alongside (not a perf finding, but worth
fixing in the same patch):** the count query's `$where` is built
*before* `survey_runs.id = :run_id2` is appended for the sibling
items query (line 264) — this count omits a filter the displayed
rows apply, so pagination totals can diverge from what's shown on
the "User Detail" admin page.

**Suggested remediation:** scope the `survey_run_units` join by
`run_id` too (fixes both the fan-out and, incidentally, aligns the
count with the items query):
```sql
LEFT JOIN survey_run_units ON survey_unit_sessions.unit_id = survey_run_units.unit_id
  AND survey_run_units.run_id = survey_run_sessions.run_id
```
and add the same `run_id2`-equivalent filter to the count `$where`
that the items query applies.

#### SQ-07 — `RunSession::getCurrentUnitSession` — the single most-executed query, filesorts for long-tenure participants
**File:** `application/Model/RunSession.php:691` · **Severity:** medium · **Verdict:** confirmed

```sql
SELECT survey_unit_sessions.unit_id, survey_unit_sessions.id, survey_unit_sessions.run_session_id,
       survey_unit_sessions.created, survey_unit_sessions.expires, survey_unit_sessions.ended,
       survey_unit_sessions.expired, survey_unit_sessions.queued, survey_units.type
FROM survey_unit_sessions
LEFT JOIN survey_units ON survey_unit_sessions.unit_id = survey_units.id
WHERE survey_unit_sessions.run_session_id = :rsid AND survey_unit_sessions.ended IS NULL
  AND survey_unit_sessions.expired IS NULL AND survey_unit_sessions.queued != -9
  AND survey_unit_sessions.unit_id = :unit_id
  AND (survey_unit_sessions.run_unit_id = :run_unit_id OR survey_unit_sessions.run_unit_id IS NULL)
ORDER BY survey_unit_sessions.id DESC LIMIT 1
```

**Why slow:** called from `execute()` on **every participant page
load and every daemon tick**. No index covers
`ended/expired/queued/unit_id` together with `ORDER BY id DESC`, so
MariaDB filters+filesorts the row's remaining `run_session` rows in
memory. Cost scales with a single participant's accumulated
`survey_unit_sessions` row count (iteration/tenure), not O(1).

**EXPLAIN evidence:** busiest real `run_session` (id=998, 1,805
unit-sessions): `ref_or_null` + rowid_filter, **774 rows
pre-filter / ~204 post-filter, `Using filesort`**. Typical
`run_session` (id=79367, 39 rows): only 6 rows, filesort negligible.
Only ~52 of 93,783 (0.055%) run_sessions on this DB have 200+
unit_sessions — medium severity reflects that long tail specifically
(diary/ESM studies with high iteration counts), not the common case.

**Suggested remediation:**
```sql
-- sketch: covers the filter set, still can't avoid filesort on id DESC
-- without also indexing id, but shrinks the pre-filesort row set
ALTER TABLE survey_unit_sessions
  ADD INDEX idx_current_lookup (run_session_id, unit_id, ended, expired, id);
```
Given the OR on `run_unit_id`, consider splitting into two narrower
queries (one for `run_unit_id = :x`, one for `run_unit_id IS NULL`)
unioned in the app, each of which *can* use a tight composite index.

**Files:** `application/Model/UnitSession.php:256` (`load`, fallback branch) and `:1086` (`getRunData`) · **Severity:** low · **Verdict:** confirmed

#### SQ-44 — `DB::__construct` — every query pays PREPARE+EXECUTE as two round trips, no statement cache
**File:** `application/DB.php:83` (+ `execute()`/`exec()` at `:117`/`:140`) · **Severity:** medium · **Verdict:** not-explainable

`PDO::ATTR_EMULATE_PREPARES => false` is set on every connection,
and every call site builds a fresh SQL string and calls
`$PDO->prepare()` inline — no statement is cached/reused across

either accept emulated prepares for read-mostly, non-identifier-
interpolated call sites (trades a folklore SQL-injection concern
that this codebase already avoids via bound params for a real 2x
round-trip saving), or add a per-request statement cache keyed by
SQL text so repeated identical queries in one request reuse their
prepared handle.

bound the underlying scan": SQ-13 (`getRunsManagementTablePdoStatement`
session counts), SQ-16/17/18 (`ComputeUsageHelper` — usage-by-user,
top-runs, instance totals), and SQ-03 (`ComputeLimitCron::
candidateUsers`, monthly compute-limit checks). All four read from
the same `survey_run_sessions`/`survey_unit_sessions` fact-table
shape. A single maintained rollup (updated incrementally when
`execution_time`/session rows are written, or refreshed on a cheap
schedule) would serve all four instead of each re-aggregating raw
history independently. The schema-tools report notes an apparently
unused `survey_resource_metrics`-shaped table already exists —
worth checking whether it was intended for exactly this and never
wired up.

**3. Composite-index batch.** SQ-04/SQ-09 (`run_unit_id`-leading
index) and SQ-07/SQ-08 (`(run_session_id, unit_id, run_unit_id, id)`-
shaped index) both target `survey_unit_sessions`, the largest table
in the schema — worth landing as one migration with both indexes
together rather than two separate ALTERs, to pay the rebuild cost
once. Validate against a production-sized snapshot (or the dynamic
capture in option 1) before committing to exact column order.
